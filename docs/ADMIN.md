## 1. Назначение и границы

Кладовка — файловое объектное хранилище с частью path-style S3 API и встроенной панелью. Один процесс обслуживает один DATA_ROOT. Запуск нескольких процессов с одним каталогом данных не поддерживается.

В версии 0.4.0 есть два режима: прежний `CLUSTER_MODE=legacy` по умолчанию и новый [consensus: автоматическое восстановление и безопасный failover](CONSENSUS.md) для 3–5 узлов с RF=N. Добавление и вывод описаны в [разделе управления составом](CONSENSUS.md#9-добавление-и-вывод-участников). Новый режим требует новых пустых каталогов/миграции и собственного пилота.

Рекомендуемый начальный режим — один узел в доверенной сети с HTTPS и резервным копированием. Legacy-кластер поддерживает синхронное копирование, но не имеет автоматического перевыбора primary, восстановления пропущенных копий и переноса данных при изменении состава. Не меняйте состав рабочего кластера без плана миграции.

## 2. Сборка и пробный запуск

Нужны Go 1.25+ и make. Go-зависимости Raft/BoltDB закреплены в go.mod/go.sum и скачиваются при первой сборке. Для запуска внешняя служба консенсуса не нужна; лицензии — в THIRD_PARTY_NOTICES.md.

```bash
make build
make test
./bin/kladovka -version
```

Для локального запуска создайте отдельный каталог и задайте свои реквизиты:

```bash
export LISTEN_ADDR=127.0.0.1:8000
export DATA_ROOT="$PWD/data"
export NODE_URL=http://127.0.0.1:8000
export ACCESS_KEY=admin
# Введите секрет; значение не записывается в историю команд.
read -r -s SECRET_KEY
export SECRET_KEY
export MAX_OBJECT_SIZE=1073741824
./bin/kladovka
```

Откройте `/ui/`: появится форма входа. Введите ADMIN_USER / ADMIN_PASSWORD, если они заданы; иначе ACCESS_KEY / SECRET_KEY. После входа панель создаёт ограниченный по времени сеанс; кнопка «Выйти» отзывает его. Через HTTP такой вход допустим только на локальной машине или в защищённом туннеле. На сервере используйте HTTPS.

Проверки из другого терминала (задайте там ACCESS_KEY; curl запросит секрет как пароль):

```bash
curl --fail http://127.0.0.1:8000/healthz
curl --fail --user "$ACCESS_KEY" http://127.0.0.1:8000/api/stats
```

## 3. Конфигурация

Параметры environment читаются при старте и требуют перезапуска. Исключение — содержимое ACCESS_POLICY_FILE: оно перечитывается на подписанных запросах. Текущий состав consensus меняется административным API и сохраняется в Raft, а не редактированием стартового RAFT_PEERS.

- `CLUSTER_MODE`: `legacy` (по умолчанию) или `consensus`. Последний использует журнал Raft, автоматическое восстановление и failover; обязательные RAFT_* параметры и условия — в [отдельной инструкции](CONSENSUS.md).
- `LISTEN_ADDR`: адрес прослушивания, по умолчанию `:8000`. Для локального запуска задавайте `127.0.0.1:8000`.
- `DATA_ROOT`: каталог данных, по умолчанию `./data`. В службе задавайте абсолютный путь.
- `ACCESS_KEY`, `SECRET_KEY`: общая пара доступа к S3 и панели в режиме совместимости без файла доступа и отдельных Basic-реквизитов. Значения по умолчанию `kladovka` / `kladovka-secret` предназначены для знакомства; перед эксплуатацией замените их.
- `ADMIN_USER`, `ADMIN_PASSWORD`: отдельный администратор панели и Basic API; задаются вместе. При ACCESS_POLICY_FILE обязательны, пароль — не менее 16 байт.
- `ACCESS_POLICY_FILE`: путь к приватному JSON-файлу пользователей/ключей версии 1; включает роли и отключает общую S3-пару. Перечитывается на подписанных запросах.
- `SESSION_TTL_SEC`: срок сеанса панели, по умолчанию 28800, диапазон 60–86400 секунд.
- `AUDIT_LOG_FILE`: путь журнала; по умолчанию DATA_ROOT/.audit.jsonl. Пользовательский путь должен быть вне DATA_ROOT. Родительский каталог должен существовать, журнал — приватный.
- `REGION`: регион подписи, по умолчанию `us-east-1`; должен совпадать у клиента и сервера.
- `NODE_ID`: идентификатор узла, по умолчанию `node-1`. В кластере обязан совпадать с `host:port` в NODE_URL.
- `NODE_URL`: базовый HTTP(S) URL без пути и query, по умолчанию `http://localhost:8000`. Должен быть доступен остальным узлам и Prometheus.
- `PEER_NODES`: базовые URL остальных узлов через запятую, без собственного узла и повторов. По умолчанию пусто.
- `REPLICATION_FACTOR`: число копий с учётом primary, по умолчанию `1`; не больше числа настроенных узлов.
- `CLUSTER_TOKEN`: общий секрет межнодового API. Задавайте одинаковое случайное значение на всех узлах. Если не задан, токен выводится из SECRET_KEY; для Prometheus SD удобнее задать явно.
- `CLUSTER_VERIFY_TLS`: проверять сертификаты пиров, по умолчанию `true`. `false` допустимо только в лаборатории.
- `HEALTH_INTERVAL_SEC`: интервал проверки пиров в секундах, по умолчанию `10`, строго больше нуля. Один health-запрос ограничен тремя секундами.
- `MAX_CONCURRENT_UPLOADS`: число одновременных локальных загрузок, по умолчанию `4`, диапазон 1–1024. При заполнении возвращается 503 с Retry-After. Чтение и статистика не занимают эти слоты; пересылка на другой primary также не занимает локальный слот.
- `MAX_TEMP_BYTES`: общий бюджет одновременно принимаемых временных тел на узле, по умолчанию 2147483648 (2 GiB), `0` отключает бюджет. Превышение даёт 507. Для одиночного обычного PUT этот бюджет тоже ограничивает размер файла.
- `STORAGE_QUOTA_BYTES`: квота суммарного содержимого объектов и multipart-частей на узле, по умолчанию `0` (без квоты). Метаданные не входят в логическую квоту. Для перезаписи и сборки multipart нужен запас под новое содержимое рядом со старым/частями; превышение возвращает 507 и не публикует частичный объект.
- `MIN_FREE_DISK_BYTES`: свободный резерв файловой системы DATA_ROOT, по умолчанию 67108864 (64 MiB), `0` отключает. Перед порциями записи проверяется доступное место; при достижении резерва возвращается 507. Это не резервирование места против сторонних процессов ОС.
- `VERIFY_OBJECT_CHECKSUM`: проверять контрольную сумму перед выдачей объекта, по умолчанию `true`. Для новых объектов сохраняется SHA-256; повреждение блокирует чтение с InvalidObjectState. Проверка полностью читает файл перед выдачей, в том числе для HEAD/Range, и увеличивает дисковую нагрузку. Отключение `false` уменьшает эту проверку, но не даёт той же защиты чтения.
- `MULTIPART_TTL_SEC`: срок без изменения multipart-загрузки, по умолчанию 86400 (24 часа), строго положительный. Свежие части обновляют время; активный HTTP-запрос, включая завершение/репликацию, защищён от TTL-очистки.
- `CLEANUP_INTERVAL_SEC`: период TTL-очистки, по умолчанию 600 секунд, строго положительный. Очистка также выполняется при старте.
- `MAX_OBJECT_SIZE`: максимальный размер объекта в байтах; `0` — без настроенного лимита. Применяется к обычным, внутренним и multipart-загрузкам, включая собранный объект. Выберите лимит по доступному месту, нагрузке и времени передачи.
- `TLS_CERT_FILE`, `TLS_KEY_FILE`: оба пути к PEM-файлам; задаются вместе. Без них сервер работает по HTTP.
- `TLS_MIN_VERSION`: `1.2` (по умолчанию) или `1.3`.

Загрузка использует DATA_ROOT/.uploads, затем журнал DATA_ROOT/.transactions и окончательный файл. Для крупных объектов предусмотрите запас места под принимаемое тело и новую копию одновременно; multipart при сборке требует место под части и полный результат. TMPDIR больше не определяет место приёма HTTP-тел. Оставшиеся после аварии upload-*.tmp очищаются при запуске. Части multipart находятся в DATA_ROOT/.multipart. Обычный PUT не буферизуется целиком в RAM.

При запуске сервер сначала восстанавливает подготовленные записи и удаления из `.transactions`, затем начинает обслуживать запросы. Журнал и SHA-256 метаданных синхронизируются перед публикацией; каталоги синхронизируются после rename/delete. Если публикация пары «объект + метаданные» оборвалась, чтение этого ключа блокируется до успешного восстановления. Неподтверждённый запрос после сбоя мог примениться — проверяйте объект или повторяйте запрос. В одном узле PUT/DELETE и публикация метаданных упорядочены; это не решает согласование конкурентных записей между узлами.

Не удаляйте `.transactions` вручную. Если запуск сообщает ошибку восстановления, освободите место/восстановите права и сохраните резервную копию журнала прежде, чем предпринимать исправления. Старые версии не умеют восстанавливать новый журнал: откат бинарника допускается только после завершения всех записей, остановки службы и проверки пустого журнала либо на совместимую резервную копию.

При первом запуске на каталоге v0.3 сервер один раз проходит существующие объекты, проверяет обычные MD5 ETag, дополняет метаданные SHA-256 и сохраняет скрытый маркер формата. Это может занять время на большом хранилище; делайте переход в окно обслуживания и после резервной копии. Старые multipart-объекты или legacy-файлы без метаданных получают исходную SHA-256 по текущим байтам — это не доказывает их целостность до обновления. После перехода отсутствие/повреждение метаданных блокирует чтение, а не отключает проверку незаметно. Сохраняйте маркер формата в резервной копии.

## 4. Установка на Linux с systemd

Создайте системного пользователя `kladovka` штатным инструментом дистрибутива, без интерактивного входа. Затем:

```bash
sudo install -m 0755 ./bin/kladovka /usr/local/bin/kladovka
sudo install -d -o kladovka -g kladovka -m 0700 /var/lib/kladovka
sudo install -d -o root -g kladovka -m 0750 /etc/kladovka
sudo install -m 0600 /dev/null /etc/kladovka/kladovka.env
sudoedit /etc/kladovka/kladovka.env
```

Содержимое env-файла (замените оба секрета):

```ini
LISTEN_ADDR=127.0.0.1:8000
DATA_ROOT=/var/lib/kladovka
NODE_ID=node-1
NODE_URL=http://127.0.0.1:8000
ACCESS_KEY=admin
SECRET_KEY=REPLACE_WITH_RANDOM_SECRET
CLUSTER_TOKEN=REPLACE_WITH_ANOTHER_RANDOM_SECRET
REGION=us-east-1
REPLICATION_FACTOR=1
MAX_OBJECT_SIZE=1073741824
```

Пример `/etc/systemd/system/kladovka.service`:

```ini
[Unit]
Description=Kladovka object storage
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=kladovka
Group=kladovka
EnvironmentFile=/etc/kladovka/kladovka.env
WorkingDirectory=/var/lib/kladovka
ExecStart=/usr/local/bin/kladovka
Restart=on-failure
RestartSec=3
TimeoutStopSec=40
UMask=0077
NoNewPrivileges=true
PrivateTmp=true
ProtectHome=true
ProtectSystem=strict
ReadWritePaths=/var/lib/kladovka

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now kladovka
sudo systemctl status kladovka
sudo journalctl -u kladovka -n 100 --no-pager
```

Если задаёте внешний AUDIT_LOG_FILE, добавьте каталог журнала в ReadWritePaths и настройте его владельца/права; одного разрешения ОС недостаточно при ProtectSystem=strict. Изменения unit-файла применяйте через daemon-reload и перезапуск в окно обслуживания.

При SIGTERM сервер прекращает приём новых соединений и ждёт активные запросы до 30 секунд. Перед остановкой для резервного копирования сначала прекратите записи со стороны клиентов; запрос, не уложившийся в срок, может быть прерван.

## 5. HTTPS и доступ

Для прямого HTTPS добавьте в env-файл:

```ini
LISTEN_ADDR=:8443
NODE_URL=https://storage.example.org:8443
TLS_CERT_FILE=/etc/kladovka/tls/fullchain.pem
TLS_KEY_FILE=/etc/kladovka/tls/key.pem
TLS_MIN_VERSION=1.2
```

Пользователь службы должен читать сертификат и ключ. Приватный ключ не публикуйте. После обновления сертификата перезапустите службу.

Маршруты имеют разную авторизацию:

- S3 (`/`, `/<полка>`, `/<полка>/<ключ>`): AWS SigV4 или presigned URL.
- `/ui/`: сеанс администратора, вход через форму `/ui/login.html`. Без сеанса панель перенаправляет на форму; Basic больше не открывает панель. Форма, её JS и CSS публичны и не содержат данных хранилища.
- `/api/*`, `/cluster`, `/metrics`: сеанс панели либо HTTP Basic с ADMIN_USER / ADMIN_PASSWORD (если заданы), иначе ACCESS_KEY / SECRET_KEY. JSON API также принимает SigV4 с ролями пользователя; полная статистика доступна только admin.
- `/api/session`: POST создаёт сеанс по JSON `user`/`password`, GET возвращает пользователя, срок и CSRF-токен, DELETE завершает сеанс с `X-CSRF-Token`. Basic/SigV4 не заменяют сеанс на этом маршруте.
- `/internal/*`: `Authorization: Bearer <CLUSTER_TOKEN>`; ограничьте доступ также сетью.
- `/healthz`: публичная проверка живого процесса; не подтверждает исправность репликации или доступность записи на диск.

Вход в панель и Basic API предоставляют полный доступ администратора. S3-ключи пользователей из файла доступа не принимаются как реквизиты панели. AWS IAM/ACL и персональные учётные записи панели для reader/writer пока отсутствуют.

При reverse proxy сохраняйте исходный Host, путь и query для SigV4. Не добавляйте Basic-авторизацию на S3-маршруты и не заменяйте заголовок Authorization клиента. Ограничьте публичный доступ к внутренним маршрутам, настройте лимиты тела и тайм-ауты передачи на proxy. Используйте собственный CA через доверенное системное хранилище, а не отключение проверки TLS.

### Сеансы панели

`SESSION_TTL_SEC` задаёт абсолютный срок сеанса: по умолчанию 28800 секунд (8 часов), допустимо 60–86400. Активность срок не продлевает. Сеансы хранятся только в памяти узла, максимум 1024; выход отзывает текущий токен, повторный вход заменяет старый токен этого браузера, перезапуск отзывает все сеансы узла. Изменение реквизитов администратора также делает старые сеансы недействительными. На другом узле требуется отдельный вход. Для пересылки записи на primary сервер использует административные Basic-реквизиты, не передавая cookie или CSRF-токен браузера; реквизиты должны совпадать на узлах.

Cookie имеет HttpOnly, SameSite=Strict, Path=/ и не сохраняется в localStorage. Secure включается при TLS или HTTPS в NODE_URL. За HTTPS reverse proxy задавайте внешний HTTPS NODE_URL и сохраняйте Host; произвольным X-Forwarded-* сервер не доверяет. Для изменяющих запросов с cookie требуется `X-CSRF-Token`, а Origin проверяется по схеме и Host. Basic и SigV4 остаются для автоматизации без cookie; не смешивайте их с cookie просроченного сеанса. Срок/ошибки сеанса не дают автоматического перехода к общей паре ключей.

Вход принимает только JSON, ограничен десятью попытками в минуту с одного сетевого адреса. За proxy этот лимит общий для его адреса: предусмотрите отдельные ограничения и правильную сетевую схему. Число адресов в памяти ограничено 4096. Секреты входа не возвращаются в ответе и не попадают в аудит. После выхода ранее начатая передача может завершиться; Basic API-реквизиты не отзываются кнопкой выхода и должны оставаться у автоматизации/администратора.

### Журнал аудита

По умолчанию журнал — `DATA_ROOT/.audit.jsonl`, права 0600. `AUDIT_LOG_FILE` позволяет выбрать отдельный файл вне DATA_ROOT; его родительский каталог должен существовать и быть доступен службе. Размещать журнал среди объектов полок нельзя. При старте недоступный или открытый другим пользователям файл не принимается. Журнал содержит имена пользователей, ключей доступа и объектов; защищайте его и резервные копии как служебные данные.

Для изменяющих HTTP-запросов записываются `attempt` до обработки и `result` с проверенным пользователем (`actor`), методом, путём, HTTP-статусом и общим `request_id`. Каждая запись синхронизируется на диск. Пароли, Secret Key, Authorization, cookies, CSRF-токены, query подписанных ссылок и тела запросов не журналируются. Внутренние запросы реплик помечаются `cluster`; исходный пользователь фиксируется на входном узле. При недоступности предварительной записи операция возвращает 503 и не начинается. Ошибка записи результата не отменяет уже выполненную операцию: она попадает в служебный лог; дальнейшие изменения блокируются до устранения причины и перезапуска. Попытка может остаться без результата и при аварии. Аудит не является транзакцией с хранилищем и не защищён от изменения владельцем файлов.

`policy_snapshot` фиксирует начальную и каждую замеченную новую конфигурацию пользователей, ролей и идентификаторов ключей; Secret Key не записываются даже при ротации. На старте также фиксируется `admin_configuration`. Источник этих изменений — `local_configuration`: сервер не устанавливает, какой человек редактировал файл или environment; для этого нужен аудит ОС. Изменение файла обнаруживается при следующем подписанном запросе или запуске. Пока конфигурация не прочитана, промежуточные правки файла не фиксируются.

Просмотр последних событий: `tail -n 50 /путь/к/.audit.jsonl`. Для ротации остановите службу, перенесите журнал в защищённый архив и запустите службу: она создаст новый файл. Ограничивайте срок хранения и следите за свободным местом; автоматической ротации нет, служебный журнал не входит в квоту объектов. При восстановлении аудит из копии сохраняет исторические события; новые добавляются в конец. После прерванной записи неполная JSON-строка отделяется новой строкой; при разборе старого хвоста учитывайте это.

### Пользователи и ключи

Для разграничения доступа задайте `ACCESS_POLICY_FILE=/etc/kladovka/access.json`, отдельные `ADMIN_USER` и `ADMIN_PASSWORD` (не менее 16 байт), а также явный `CLUSTER_TOKEN`. Basic-реквизиты администратора задаются вместе; без файла доступа их тоже можно отделить от общей S3-пары. Передавайте секреты через защищённый environment-файл службы.

Файл доступа должен быть обычным файлом размером не более 1 MiB и с правами `0600` (доступен владельцу службы). Храните его вне DATA_ROOT и Git. Пример структуры с демонстрационными секретами, которые необходимо заменить:

```json
{
  "version": 1,
  "users": [
    {
      "id": "backup-reader",
      "role": "reader",
      "polki": ["backups"],
      "keys": [
        {"access_key": "backup-reader-1", "secret_key": "REPLACE-WITH-RANDOM-SECRET-1"},
        {"access_key": "backup-reader-2", "secret_key": "REPLACE-WITH-RANDOM-SECRET-2"}
      ]
    },
    {
      "id": "photo-uploader",
      "role": "writer",
      "polki": ["photos"],
      "keys": [{"access_key": "photo-uploader-1", "secret_key": "REPLACE-WITH-RANDOM-SECRET-3"}]
    }
  ]
}
```

Роль `reader` разрешает LIST/GET/HEAD существующих объектов в перечисленных полках. `writer` дополнительно разрешает PUT/DELETE объектов и все операции multipart в этих полках. Это доступ ко всей полке, включая multipart других писателей этой полки. Создавать и удалять полки может только `admin`. Роль `admin` в файле даёт S3-клиенту полный доступ ко всем полкам и JSON API; пароль панели она не создаёт. Подстановок и наследования имён полок нет. Список полок через S3 и JSON фильтруется по правам; статистика всего узла, метрики и панель остаются административными. Полки заранее создаёт администратор.

ID пользователей и Access Key должны быть уникальны во всём файле; у пользователя может быть несколько ключей или ни одного. Secret Key должен содержать не менее 16 байт; для рабочих ключей используйте длинные случайные значения. Секреты хранятся в файле открытым текстом, поскольку нужны для проверки SigV4, поэтому защищайте файл и его резервные копии.

При заданном ACCESS_POLICY_FILE общая S3-пара ACCESS_KEY / SECRET_KEY отключается. Файл проверяется при старте и заново для каждого подписанного запроса. Для выдачи/отзыва ключа или изменения роли подготовьте полный новый файл с правами 0600 рядом с действующим и замените его атомарным rename, например `mv /etc/kladovka/access.new /etc/kladovka/access.json`, сохранив владельца службы. Удаление записи ключа отзывает также его presigned URL на новых запросах. Уже выполняющаяся передача может завершиться с ранее проверенными правами. Ошибочный, отсутствующий или слишком открытый файл блокирует подписанный доступ; возврата к общей паре и старому снимку нет. Административный доступ остаётся для восстановления конфигурации. Смена Basic-реквизитов требует перезапуска службы.

Не редактируйте файл на месте: частично записанный JSON временно блокирует доступ. На всех узлах кластера установите одинаковые файлы доступа и Basic-реквизиты; централизованной доставки и атомарного отзыва сразу на всех узлах пока нет. До обновления последнего узла старые ключи на нём действуют. Резервируйте конфигурацию доступа отдельно от данных и не восстанавливайте отозванные ключи из старой копии без проверки.

## 6. Кластеризация и RF

### Consensus: порядок эксплуатации

Этот подраздел относится к `CLUSTER_MODE=consensus`. Подразделы 6.1–6.9 ниже описывают legacy. Полная конфигурация, TLS и команды управления составом находятся в [руководстве consensus](CONSENSUS.md).

#### Первоначальная настройка

1. Используйте 64-битную сборку версии 0.4.0, отдельные серверы и пустой DATA_ROOT на каждом. Подготовьте исходную группу из 3 или 5 участников. На трёх узлах нужно большинство 2, на пяти — 3. Позже состав можно изменять в пределах 3–5 через API.
2. Настройте одинаковые RAFT_CLUSTER_ID, исходный RAFT_PEERS, REPLICATION_FACTOR, регион, межузловой токен и правила доступа. NODE_ID должен совпадать с host:port собственного NODE_URL. На каждом сервере PEER_NODES содержит остальные первоначальные HTTP-адреса.
3. Настройте HTTP TLS и отдельный Raft listener/TLS по [примеру трёх серверов](CONSENSUS.md#4-пример-трёх-серверов). Проверьте SAN сертификатов, доверенный CA, доступность HTTP и Raft-портов между участниками. Каждый сервер получает собственный DATA_ROOT и подходящий сертификат.
4. Выполните первичное создание группы с RAFT_BOOTSTRAP по инструкции. После создания сохраните конфигурацию, используйте RAFT_BOOTSTRAP=false для обычных последующих запусков. При утрате данных не применяйте bootstrap для восстановления большинства.
5. Создайте контрольную полку и объект через S3. Скачайте его через разные действующие endpoint, сравните SHA-256. Проверьте `/cluster`, каталог, журнал службы и метрики. Ввод в эксплуатацию требует пилота, а не одного успешного health-запроса.

RF=N означает целевое число полных копий. Кворум подтверждает запись раньше, чем обязательно завершится восстановление каждой реплики. RF=4 требует 3 голоса и выдерживает только один отказ, как группа из трёх. Размер WAL, снимков и блоков расходует дополнительный диск сверх видимых объектов.

#### Ежедневная проверка

Задайте адрес конкретного узла и имя администратора. Curl запросит пароль отдельно:

```bash
export ENDPOINT=https://s1.storage.example.org:8443
export ADMIN_USER=operator
curl --fail "$ENDPOINT/healthz"
curl --fail --user "$ADMIN_USER" "$ENDPOINT/cluster"
curl --fail --user "$ADMIN_USER" "$ENDPOINT/metrics"
```

На каждом участнике `/cluster` показывает локальное наблюдение роли, `raft_id`, лидера и состава. Сверяйте `voters`, `quorum`, `target_rf`, `repair_pending` и `repair_error`. Ожидающий добавления узел ещё не обслуживает пользовательские данные. HTTP health и наличие адреса лидера не подтверждают кворум: для проверки обслуживания используйте чтение контрольного объекта.

Проверяйте доступное службе место, ошибки измерения, состояние discovery Prometheus и алерты. Диск на `/api/stats` или в панели consensus может относиться к лидеру, обслужившему запрос; для конкретной реплики смотрите её `/metrics`. Политики доступа, сертификаты и внешний аудит требуют отдельной согласованной доставки и резервирования, журнал объектов их не синхронизирует.

#### Узел временно недоступен, диск сохранён

Восстановите сеть, место на диске или службу, затем запустите **тот же DATA_ROOT с прежней идентичностью**. Догоняющая репликация выполняется автоматически. Наблюдайте ошибки и очередь восстановления, проверяйте контрольные объекты. Не удаляйте `.consensus` и не выполняйте RAFT_JOIN для обычного возврата узла.

Если отказал лидер, исправное большинство выбирает нового. Доступные входные узлы пересылают запросы новому лидеру. Клиентов остановленного endpoint переключает внешний балансировщик или сам клиент. Незавершённый multipart прежнего лидера может потребовать повторной загрузки. При потере большинства сначала восстановите участников с их сохранёнными данными.

#### Диск потерян: замена участника

Замена сохраняет логический HTTP-слот, но создаёт новую Raft-инкарнацию. Нужны действующее большинство, изолированный прежний процесс, новый пустой DATA_ROOT и **никогда ранее не использовавшийся в группе порт Raft**. Новая машина не должна принимать старый Raft-порт. Приём выполняет `/api/cluster/replace`, после стадии Nonvoter и проверки данных. Подготовка и точные команды — [замена потерянного узла](CONSENSUS.md#8-замена-потерянного-узла-новым-сервером).

Не восстанавливайте пустой raft.db под старым голосующим raft_id. Не переносите случайную более старую копию поверх живой группы. Потеря большинства постоянных данных требует отдельного восстановления из проверенной резервной копии.

#### Добавление и вывод

Используйте административные `/api/cluster/add` и `/api/cluster/remove` из [процедуры изменения состава](CONSENSUS.md#9-добавление-и-вывод-участников). Сначала обновите участников до поддерживающей этот протокол сборки. Для нового участника нужны отдельный HTTP-адрес, DATA_ROOT и новый Raft-порт. Добавление проходит через неголосующую реплику с проверкой SHA-256 и индекса.

Вывод требует проверки кворума оставшихся участников. При выводе текущего лидера кластер передаёт лидерство. Ниже трёх и выше пяти голосующих участников API не допускает. Операции состава и замены выполняются последовательно.

Ответ 202 означает сохранённое намерение. Дождитесь `membership_change.done=true` или `replacement.done=true` **на текущем лидере**, проверьте состав и данные. Только затем останавливайте выведенный процесс и убирайте его из балансировщика. Файлы выведенного узла автоматически не удаляются.

Сохраняйте request_id для повторов добавления/вывода. Потеря ответа не требует нового идентификатора. После рестарта операция продолжится, если сохранился DATA_ROOT кандидата. Отмена и переназначение незавершённой операции после утраты этого диска пока не реализованы.

**Не переписывайте первоначальные RAFT_PEERS и REPLICATION_FACTOR вслед за живым составом.** Они входят в проверку дисковой идентичности; текущая топология и целевой RF хранятся в Raft. Индивидуальные настройки нового узла описаны в процедуре добавления.

#### Плановая остановка и обновление

В опубликованной v0.4.0 drain API нет. В следующей разработке добавлен сохранённый в Raft режим enter/check/exit: см. [CONSENSUS, раздел 10](CONSENSUS.md#10-плановое-обслуживание-узла-после-v040). Для v0.4.0 используйте ручной порядок ниже. До остановки проверьте текущее большинство и незавершённые операции состава, завершите или отмените multipart и подготовьте резервную копию. Выведите endpoint из клиентского балансировщика. Останавливайте один узел за раз, возвращая его и проверяя восстановление перед следующей остановкой. Для обновления согласуйте окно без записей и следуйте разделу 9. Передача лидерства при выводе из состава не является универсальным режимом обслуживания.

Не считайте успешный GET через остановленный ранее адрес доказательством, что все локальные файлы уже восстановлены: запрос может обслужить лидер. Смотрите локальные ошибки/очередь и выполняйте приёмочные проверки на изолированном стенде.



### 6.1. Что означает RF

`RF` — сокращение от `REPLICATION_FACTOR`, числа **полных копий каждого объекта, включая primary**. Primary — основной узел именно для пары «полка + ключ», а не единственный ведущий всего кластера. У разных объектов могут быть разные primary. Реплика — дополнительная полная копия объекта на другом процессе/узле; это не часть файла и не резервная копия прошлой версии.

Примеры для исправной конфигурации и успешно завершённых записей:

- Один узел, `RF=1`: одна локальная копия; при потере её диска нужны резервные данные.
- Два узла, `RF=2`: каждый объект хранится на обоих узлах. Запись требует обоих; доступность одного узла сама по себе не обеспечивает запись.
- Три узла, `RF=2`: каждый объект хранится на двух из трёх узлов; разные объекты получают разные пары. У третьего узла может не быть этого объекта в локальном списке.
- Три узла, `RF=3`: каждый объект хранится на всех трёх; запись требует всех трёх.
- Три узла, `RF=4`: недопустимо, процесс отклонит конфигурацию при старте.

**Особенность текущей версии: `RF=1` выключает пересылку PUT/DELETE, репликацию, поиск объекта на пирах и распространение операций с полками.** Несколько процессов с RF=1 и заполненным PEER_NODES остаются независимыми хранилищами, а не кластером с распределением по одному экземпляру. Для описанной ниже межузловой работы нужны `RF>1` и одинаковый состав у всех узлов.

RF не является кворумом. При RF=3 ответ от двух узлов не считается успешной записью. RF также не означает «можно потерять RF−1 узлов и продолжать все операции»: сохранившаяся копия может сохранить байты, но запись требует primary и всех назначенных реплик. Репликация повторяет ошибочное удаление/перезапись, поэтому не заменяет независимую резервную копию.

### 6.2. Размещение и путь запроса

Каждый узел строит один и тот же список NODE_ID из себя и PEER_NODES, сортирует его лексикографически и выбирает primary по хешу `полка/ключ`. Остальные RF−1 узлов берутся последовательно из этого списка с переходом через конец. Используется SHA-256 с постоянным seed и индекс по модулю числа узлов; свободное место, мощность узла и health при выборе не учитываются. Порядок перечисления адресов в PEER_NODES неважен: важны одинаковый набор участников и точные строки их идентификаторов. Это не динамический балансировщик и не механизм выбора нового primary.

Например, для некоторого ключа primary — B, следующая реплика — C. При трёх узлах и RF=2:

1. Клиент отправляет PUT на A, B или C.
2. Если запрос пришёл не на B, принимающий узел пересылает его B. Смена клиентского endpoint не меняет primary этого ключа.
3. B принимает тело, проверяет ограничения и сохраняет объект локально.
4. B передаёт полную копию C и ждёт успешного ответа.
5. Только после подтверждения копирования клиент получает успешный ответ. A в этом примере не получает копию только потому, что принял клиентский запрос.

При ошибке шага 4 возвращается 503, но новая версия на B уже может существовать. Между локальной публикацией и завершением репликации другой запрос также может увидеть новую локальную версию. Межузловой транзакции, отката всех копий и глобального упорядочения конкурирующих операций нет. Не допускайте параллельных записей/удалений одного ключа разными клиентами; согласуйте одного писателя или внешнюю блокировку.

DELETE аналогично сначала выполняется на primary, затем на назначенных репликах. После частичного отказа старый объект может оставаться на реплике. При отсутствии локального файла GET может найти эту старую копию: журналов удалений (tombstones) и сверки версий пока нет. После устранения причины повторите DELETE для того же ключа, убедившись, что его не создал заново другой клиент.

GET/HEAD сначала читают локальный объект. При его отсутствии и RF>1 сервер опрашивает назначенные узлы. Локальная исправная, но устаревшая копия не сравнивается с остальными; локальное повреждение не запускает автоматическое восстановление. GET, обслуженный с другого узла, не сохраняет копию на принимающем узле. При недоступности всех подходящих копий возможен NoSuchKey: это не доказательство, что байты отсутствуют на отключённом диске.

LIST, список полок/объектов панели и статистика — **локальные**. Объект может скачиваться по точному ключу через узел, в LIST которого его нет. При RF<N строить полный каталог нужно объединением списков всех узлов с устранением повторов. При RF=N каталоги совпадают только для согласованно завершённых операций; ошибки могут оставить различия.

Полки при RF>1 создаются/удаляются на всех настроенных узлах, независимо от RF конкретного объекта. Поэтому недоступный третий узел может сорвать создание полки даже при RF=2, хотя запись существующего объекта в пару из двух доступных узлов ещё возможна. Частичные изменения полок не откатываются. Повтор создания может вернуть BucketAlreadyOwnedByYou после исправления связи — проверьте наличие полки на каждом узле. Для удаления проверьте, что она пуста на всех узлах.

### 6.3. Что согласовать до запуска

- Один список уникальных стабильных адресов узлов и одинаковый RF. На каждом узле в PEER_NODES должны быть **все остальные** узлы, без себя; суммарный состав должен совпадать. Сервер проверяет локальную конфигурацию, но не сравнивает её целиком с конфигурациями соседей.
- NODE_ID каждого узла строго равен `host:port` из его NODE_URL. DNS-имя, IP, порт и регистр строки идентификатора не меняйте произвольно: они влияют на размещение. Нельзя считать два разных адреса одного процесса двумя независимыми копиями.
- Одинаковые REGION, CLUSTER_TOKEN, S3-ключи/политики и административные реквизиты; отдельные DATA_ROOT, диски и процессы. Один DATA_ROOT нельзя разделять между процессами, в том числе через общий сетевой каталог.
- Доступ от каждого узла ко всем остальным по NODE_URL: health, пересылка, репликация и чтение идут через эти адреса. В кластере NODE_URL не должен указывать на общий балансировщик или случайную другую ноду. Для контейнеров localhost означает сам контейнер, если сеть не настроена иначе.
- HTTPS с доверенными сертификатами и подходящими DNS-именами; CLUSTER_VERIFY_TLS=true. Доверенный внутренний CA установите в системное хранилище доверия каждого сервера. На клиенте используйте AWS_CA_BUNDLE. Не путайте TLS-доверие с авторизацией: CLUSTER_TOKEN нужен отдельно.
- Доступ клиентов только к необходимым маршрутам, межузловой доступ к `/internal/*` — только доверенным участникам и средствам мониторинга. Синхронизация часов нужна для SigV4.
- Запас диска, ограничения размера/временных тел и аудит на **каждой** предполагаемой реплике. Успех записи зависит от лимитов самого ограниченного узла её размещения. Реплики тоже принимают временное тело, занимают локальные upload-слоты и проверяют квоту/свободное место.

Межузловой HTTP-клиент имеет общий тайм-аут 2 минуты на запрос, health-запрос — 3 секунды. Большая передача на медленной сети может завершиться ошибкой по этому тайм-ауту; отдельного параметра его изменения сейчас нет. Лимит размера объекта не гарантирует, что его удастся передать за это время. Проверяйте целевые размеры и скорость на своём стенде.

Два процесса на одном сервере помогают проверить протокол, но не защищают от отказа этого сервера, питания или общего диска. У модели размещения нет учёта стоек/зон отказа.

### 6.4. Конфигурация двух узлов с RF=2

Сначала выполните установку из раздела 4 на каждом сервере. Ниже содержимое env-файлов для изолированной лабораторной сети. Замените демонстрационные секреты одинаковыми случайными значениями на обоих серверах; данные в примере хранятся на разных машинах. В рабочей сети включите HTTPS по разделу 5.

Узел A, `/etc/kladovka/kladovka.env`:

```ini
LISTEN_ADDR=:8000
DATA_ROOT=/var/lib/kladovka
NODE_ID=10.0.0.10:8000
NODE_URL=http://10.0.0.10:8000
PEER_NODES=http://10.0.0.11:8000
REPLICATION_FACTOR=2
REGION=us-east-1
ACCESS_KEY=cluster-client
SECRET_KEY=REPLACE_WITH_SHARED_S3_SECRET
ADMIN_USER=operator
ADMIN_PASSWORD=REPLACE_WITH_SHARED_ADMIN_PASSWORD
CLUSTER_TOKEN=REPLACE_WITH_SHARED_CLUSTER_TOKEN
CLUSTER_VERIFY_TLS=true
HEALTH_INTERVAL_SEC=10
MAX_OBJECT_SIZE=1073741824
MAX_TEMP_BYTES=2147483648
MIN_FREE_DISK_BYTES=67108864
```

Узел B: тот же файл, кроме трёх строк:

```ini
NODE_ID=10.0.0.11:8000
NODE_URL=http://10.0.0.11:8000
PEER_NODES=http://10.0.0.10:8000
```

DATA_ROOT может иметь одинаковый текстовый путь на разных серверах, но это должны быть разные физические каталоги. При двух процессах на одной машине задайте разные пути, LISTEN_ADDR и порты NODE_URL/NODE_ID.

Для разграничения доступа добавьте на обоих узлах одинаковый `ACCESS_POLICY_FILE=/etc/kladovka/access.json` по разделу «Пользователи и ключи». В этом режиме ACCESS_KEY/SECRET_KEY перестают давать S3-доступ: создайте отдельные ключи в файле и настройте ими AWS CLI. Файл политики должен читаться пользователем службы. Если `/etc/kladovka` принадлежит root и имеет режим 0750, задайте группу `kladovka` этому каталогу или выдайте эквивалентный доступ; файл с режимом 0600 должен принадлежать `kladovka`. EnvironmentFile может оставаться root:root 0600 — systemd читает его до смены пользователя службы.

Запустите службу на **обоих** серверах, затем создавайте полки. Сначала проверьте живой процесс, административный доступ и межузловую связность на каждом узле по следующему подразделу.

### 6.5. Три узла: RF=2 или RF=3

Для трёх серверов с прямым HTTPS используйте следующие индивидуальные блоки. Общие параметры доступа, REGION, DATA_ROOT, лимиты и TLS_MIN_VERSION берутся из предыдущего примера/раздела 5. На каждом сервере нужны его сертификат и ключ; DNS должен разрешаться со всех участников.

A:

```ini
LISTEN_ADDR=:8443
NODE_ID=s1.storage.example.org:8443
NODE_URL=https://s1.storage.example.org:8443
PEER_NODES=https://s2.storage.example.org:8443,https://s3.storage.example.org:8443
REPLICATION_FACTOR=2
TLS_CERT_FILE=/etc/kladovka/tls/fullchain.pem
TLS_KEY_FILE=/etc/kladovka/tls/key.pem
```

B:

```ini
LISTEN_ADDR=:8443
NODE_ID=s2.storage.example.org:8443
NODE_URL=https://s2.storage.example.org:8443
PEER_NODES=https://s1.storage.example.org:8443,https://s3.storage.example.org:8443
REPLICATION_FACTOR=2
TLS_CERT_FILE=/etc/kladovka/tls/fullchain.pem
TLS_KEY_FILE=/etc/kladovka/tls/key.pem
```

C:

```ini
LISTEN_ADDR=:8443
NODE_ID=s3.storage.example.org:8443
NODE_URL=https://s3.storage.example.org:8443
PEER_NODES=https://s1.storage.example.org:8443,https://s2.storage.example.org:8443
REPLICATION_FACTOR=2
TLS_CERT_FILE=/etc/kladovka/tls/fullchain.pem
TLS_KEY_FILE=/etc/kladovka/tls/key.pem
```

RF=2 оставляет по одной дополнительной копии, RF=3 — по две. Для **нового пустого** кластера с RF=3 замените REPLICATION_FACTOR на 3 во всех трёх файлах до запуска. Увеличение RF в заполненном кластере само по себе не создаёт недостающие копии старых объектов; порядок изменения описан ниже.

Оценка места: для множества равномерно распределённых объектов на N одинаковых дисках по C доступных байт теоретический объём содержимого около `N × C / RF` при RF>1. Например, три диска по 1 TB и RF=2 дают около 1.5 TB до метаданных, журналов, временных тел и резервов; при RF=3 — около 1 TB. Это оценка, а не гарантированная ёмкость: отдельная пара узлов может заполниться раньше, разные размеры дисков не учитываются размещением, а большой объект должен помещаться с временными копиями на каждом назначенном узле.

### 6.6. Приёмка кластера

В примере ниже выполняется запись одного **нового тестового объекта**. Используйте отдельный AWS-профиль с административным S3-ключом: Basic-реквизиты панели не заменяют S3-ключ при включённом файле политик. В URL/путях замените адреса на реальные. Команды не останавливают узлы.

```bash
export AWS_PROFILE=kladovka
export AWS_REQUEST_CHECKSUM_CALCULATION=when_required
export AWS_RESPONSE_CHECKSUM_VALIDATION=when_required
export A=http://10.0.0.10:8000
export B=http://10.0.0.11:8000
export ADMIN_USER=operator
# Введите действующий пароль панели, не добавляя его литералом в историю.
read -r -s ADMIN_PASSWORD
export ADMIN_PASSWORD

curl --fail "$A/healthz"
curl --fail "$B/healthz"
curl --fail --user "$ADMIN_USER:$ADMIN_PASSWORD" "$A/cluster"
curl --fail --user "$ADMIN_USER:$ADMIN_PASSWORD" "$B/cluster"
```

На обоих узлах ожидаются один состав, RF=2, разные this_node и все узлы healthy. Дождитесь нескольких health-опросов; на старте соседи временно помечены недоступными. Одна успешная `/healthz` не доказывает правильность токена или возможность репликации. При ошибке проверяйте связи **в обе стороны**, ACL/firewall, сертификаты, совпадение CLUSTER_TOKEN и журналы службы. Health-статус не исключает узел из размещения и не проверяет его объекты/политику доступа.

```bash
# Имя должно быть новым в вашем хранилище.
export CHECK_BUCKET=cluster-check-$(date -u +%Y%m%d-%H%M%S)
export CHECK_DIR=$(mktemp -d)
aws --endpoint-url "$A" s3api create-bucket --bucket "$CHECK_BUCKET"
printf 'cluster acceptance check\n' > "$CHECK_DIR/cluster-check.txt"
aws --endpoint-url "$A" s3 cp "$CHECK_DIR/cluster-check.txt" "s3://$CHECK_BUCKET/check.txt"
aws --endpoint-url "$B" s3 cp "s3://$CHECK_BUCKET/check.txt" "$CHECK_DIR/cluster-check-from-b.txt"
sha256sum "$CHECK_DIR/cluster-check.txt" "$CHECK_DIR/cluster-check-from-b.txt"

# Проверка именно локальных списков, а не чтения через fallback.
curl --fail --user "$ADMIN_USER:$ADMIN_PASSWORD" "$A/api/polki/$CHECK_BUCKET"
curl --fail --user "$ADMIN_USER:$ADMIN_PASSWORD" "$B/api/polki/$CHECK_BUCKET"
```

Если создание тестовой полки завершилось ошибкой, сначала устраните причину; при занятом имени выберите другое, не перезаписывайте существующую полку. Не продолжайте загрузку после неразобранной ошибки создания.

На macOS вместо sha256sum используйте `shasum -a 256`. Оба хеша должны совпадать. При двух узлах/RF=2 check.txt должен присутствовать в обоих локальных списках; само скачивание с B без списка ещё не доказывает наличие копии на B. Для трёх узлов/RF=2 проверьте все три локальных списка: ожидаются две копии; для RF=3 — три. Дополнительно, при остановленных записях и доверенном доступе к серверам, сравните файл `DATA_ROOT/<полка>/check.txt` на назначенных дисках и его метаданные. Не редактируйте их для проверки.

После приёмки удалите **только созданные тестовые данные**:

```bash
aws --endpoint-url "$A" s3api delete-object --bucket "$CHECK_BUCKET" --key check.txt
aws --endpoint-url "$A" s3api delete-bucket --bucket "$CHECK_BUCKET"
```

Дождитесь успеха и проверьте отсутствие тестового объекта/полки на всех узлах. Не используйте этот тест с полкой или ключом, в которых уже лежат пользовательские данные.

### 6.7. Отказы: какие операции останутся доступны

- **Отключён primary объекта.** Клиент может прочитать имеющуюся копию через доступный endpoint/реплику; успешный GET зависит от наличия подходящей копии и связности. PUT, DELETE и multipart этого ключа не переключатся на нового primary и завершатся ошибкой/тайм-аутом.
- **Primary доступен, одна назначенная реплика недоступна.** Запись может локально примениться, но клиент получит 503. Другой свободный узел вместо недоступной реплики автоматически не выбирается. При двух узлах/RF=2 это относится ко всем объектам.
- **Недоступен узел, не входящий в размещение данного объекта.** PUT/DELETE существующего объекта в доступную пару могут пройти; операции с полками всё равно затрагивают всех настроенных участников. Другие ключи могут зависеть от отключённого узла.
- **Узел вернулся со старым диском.** Он снова отвечает на health, но пропущенные записи/удаления автоматически не догоняются. Нужны проверка данных и повтор согласованных операций; успешные старые объекты сами не перезаписываются на восстановленный диск.
- **Сетевое разделение.** Ключи, для которых разорваны связи с primary/назначенными репликами, не получают полного подтверждения. Глобального consensus/fencing нет; не изменяйте состав/RF в разных частях сети и не запускайте независимые писатели одного ключа.
- **Повреждена локальная копия.** Проверка целостности может вернуть InvalidObjectState; чтение исправной реплики не означает, что повреждённая локальная копия будет исправлена автоматически. Сначала сохраните доказательства/копию и выберите проверенный источник восстановления.

503, сетевой тайм-аут или потеря ответа означают **неопределённый для клиента итог**, а не «операция точно не выполнилась». Прекратите конкурирующие изменения ключа, проверьте копии/аудит, устраните причину и повторите тот же PUT с теми же байтами либо DELETE. Для CompleteMultipartUpload части сохраняются после ошибки репликации, но уже успешное завершение, чей ответ потерялся, могло удалить UploadId; при NoSuchUpload проверьте готовый объект, прежде чем начинать заново.

Для учебной проверки отказов сначала создайте и проверьте тестовый объект в отдельном стенде, остановите одну службу штатным systemctl, проверьте GET и ожидаемый отказ PUT, затем верните службу. Не запускайте такой сценарий на рабочем кластере без окна обслуживания; отказавший PUT мог оставить объект, который нужно согласованно удалить/дописать после восстановления. Возврат всех healthy недостаточен для завершения проверки — нужны сверка байтов и локальных каталогов.

### 6.8. Обслуживание, замена узла и изменение RF

**Плановая остановка:** прекратите клиентские записи, дождитесь активных загрузок, остановите службу. Даже поочерёдный рестарт узлов уменьшает доступность записи: текущий протокол не даёт режима непрерывной записи во время обслуживания. Смена NODE_ID/адреса только ради исключения отключённого узла недопустима.

**Возврат того же узла:** сохраните прежние NODE_ID/NODE_URL, RF и состав. Если диск цел и во время остановки записи не выполнялись, запустите службу, проверьте журнал восстановления, health, чтение/хеши и локальные объекты. Если были ошибки/попытки записи, отдельно разберите эти ключи и повторите нужные операции после восстановления всей связности.

**Потеря диска:** остановите записи, сохраните оставшиеся данные и конфигурацию. Восстановите исходный DATA_ROOT этого узла из проверенной резервной копии с совместимым бинарником и прежней идентичностью. Резервная копия может быть старее остальных узлов; не возвращайте такой узел в обслуживание без сверки изменённых/удалённых ключей. Для недостающих объектов используйте подтверждённый источник байтов и повторный клиентский PUT при доступных назначенных узлах. Для удалений нужна история/авторитетный каталог, иначе устаревшие файлы могут вернуться. Если источника нет, RF не восстановит утраченные данные.

**Добавление/удаление сервера, смена NODE_ID/порта или RF:** автоматической миграции и ребаланса нет. Простая правка env и рестарт не является процедурой расширения. Изменение числа/порядка идентификаторов меняет маршрутизацию, а смена RF не пересоздаёт старые копии и не удаляет лишние. Нельзя временно снизить RF и считать, что после его возврата реплики выровняются.

Для изменения заполненного кластера используйте контролируемую миграцию:

1. Остановите записи во всех клиентах и узлах доступа; сделайте остановленные резервные копии **всех** DATA_ROOT и конфигураций. Сохраните исходный состав/RF.
2. Составьте объединённый манифест полок и ключей всех старых узлов. Для совпадающих ключей с разными байтами определите правильную версию по источнику данных/истории операций; локальный timestamp или ETag сами по себе не решают конфликт.
3. Поднимите отдельный пустой кластер с новой конфигурацией и новыми каталогами, проверьте его тестовым объектом. Не запускайте старую и новую конфигурации поверх одних файлов.
4. Скачайте выбранные объекты из проверенных источников старого хранилища и загрузите в новое через S3 с сохранением нужных ключей и Content-Type. В опубликованной v0.4.0 для этого нужен GET → локальный файл → PUT. В следующей разработке CopyObject работает между полками одного хранилища; для независимых установок по-прежнему нужны GET и PUT. Не используйте слепую файловую синхронизацию разных узлов.
5. Сравните манифест, SHA-256 байтов и количество локальных копий каждого перенесённого объекта с новым RF; проверьте политики, multipart/лимиты и клиентские операции. Multipart-загрузки лучше завершить/отменить до миграции; их UploadId не переносится простым клиентским PUT.
6. Переключите клиентов на новый endpoint, повторно проверьте подписи/сеансы и только затем возобновите записи. Старые данные сохраняйте до подтверждения результата и окончания выбранного периода восстановления.

Это процедура с остановкой записей, а не готовая команда live-rebalance. При отсутствии полного проверенного каталога и источника конфликтующих версий сначала восстановите их, а не меняйте размещение.

### 6.9. Балансировщик, multipart и резервные копии

Общий клиентский адрес может скрыть сетевые адреса узлов, но не добавляет глобальный LIST, выбор нового primary или самовосстановление. Нельзя использовать его как NODE_URL нескольких узлов. При проектировании proxy сохраняйте исходный Host/путь/query подписи и корректные тайм-ауты крупных запросов. Browser-сеансы локальны узлу: произвольное переключение backend может приводить к повторному входу; готовая конфигурация балансировщика с кластерными сеансами не предоставляется.

Части multipart хранятся на primary и не копируются на RF узлов как самостоятельные части. Реплицируется завершённый объект после сборки. Потеря primary/его диска может прервать незавершённую загрузку независимо от RF. Сохраняйте UploadId и ETag частей, используйте один endpoint и неизменный состав кластера, учитывайте TTL загрузки.

RF — текущее число назначенных копий; резервная копия — отдельная история восстановления от удаления, повреждения и административной ошибки. Для согласованной резервной копии прекращайте записи во всём кластере и сохраняйте все DATA_ROOT, в том числе скрытые журналы/маркер формата, политики, environment, сертификаты и версию программы. Подробности — в разделе 8. Одной локальной копии узла с RF<N для полного восстановления кластера недостаточно.

## 7. Мониторинг

В панели смотрите счётчики операций, трафик, состояние узлов и ошибки репликации. Счётчики и uptime сбрасываются при рестарте. Диск показывает всю файловую систему DATA_ROOT; в legacy размеры объектов показывают только локальные объекты без sidecar и multipart-частей. В consensus размеры и количество объектов относятся к общему подтверждённому каталогу, а диск — к файловой системе обслуживающего запрос узла.

Пример Prometheus: [monitoring/prometheus.yml](../monitoring/prometheus.yml). Замените endpoint, Basic username и пути к файлам секретов. В `kladovka-secret` хранится ADMIN_PASSWORD (либо SECRET_KEY в режиме общей пары), в `kladovka-cluster-token` — явно заданный CLUSTER_TOKEN; оба файла должны быть доступны только Prometheus и администратору. Для HTTPS используйте HTTPS URL SD и доверенный CA.

Правила, проверяемые сценарии и действия по каждому алерту находятся в [руководстве мониторинга](../monitoring/README.md). Доставка требует отдельной настройки Alertmanager.

Следите за `up`, `kladovka_cluster_node_healthy`, ростом `kladovka_replication_failed_total`, свободным местом файловой системы, HTTP 5xx и временем ответа. `/metrics` и `/api/stats` не заменяют проверку чтения контрольного объекта. HTTP-счётчик растёт и от опросов панели.

## 8. Резервное копирование и восстановление

1. Остановите поступление новых записей во всю группу, дождитесь завершения загрузок и операций изменения состава. Зафиксируйте состав, соответствие NODE_ID каталогам и версию бинарника.
2. Остановите службы **всех участников** для согласованной копии. На каждом сервере выполните: `sudo systemctl stop kladovka`.
3. В consensus-режиме обязательно сохраняйте `.consensus` и `.kladovka-consensus`: видимые полки являются только локальными представлениями. Скопируйте весь DATA_ROOT вместе со скрытыми каталогами, журналом `.transactions`, частями `.multipart` и файлами `*.kladovka-meta.json`. Не копируйте только видимые полки: это потеряет контекст восстановления. В кластере сделайте согласованные копии всех узлов.
4. Отдельно сохраните env-файлы, файлы политик доступа, внешний AUDIT_LOG_FILE (если задан), TLS-материалы и версию бинарника в защищённое хранилище.
5. Запустите службу и проверьте чтение контрольного объекта.

Пример копирования на отдельный том при остановленной службе:

```bash
sudo rsync -a /var/lib/kladovka/ /mnt/backup/kladovka/
```

При восстановлении остановите службы, восстановите каждый каталог в отдельный пустой DATA_ROOT, верните владельца `kladovka:kladovka`, конфигурацию и совместимую версию бинарника. Для consensus сохраняйте соответствие каталога исходной идентичности NODE_ID и адресов. Проверяйте восстановление в изолированной сети с соответствующим DNS/адресами, исключив связь с исходной группой и одновременную работу двух копий одной идентичности. Не меняйте RAFT_PEERS, чтобы обойти проверку маркера.

После запуска восстановленной группы проверьте выбор лидера, состав, LIST и скачивание контрольных объектов с SHA-256. Проверка резервной копии должна включать собственно восстановление и чтение, а не только наличие архива. Не проверяйте её поверх единственной рабочей копии. Запишите дату проверки, версию, состав, проверенные объекты и результат. Шифрование копии и доступ к сохранённым секретам настройте отдельно.

Не редактируйте файлы объектов и метаданные вручную при работающем процессе. Не очищайте `.multipart` во время загрузок. Старые неактивные multipart очищаются по TTL. Для немедленной отмены известной загрузки используйте S3 AbortMultipartUpload. Согласуйте TTL с пользователями: он ограничивает срок ручного возобновления после длительного перерыва.

## 9. Обновление и диагностика

Перед обновлением сделайте резервную копию и проверьте новую сборку на копии данных. Остановите службу, замените бинарник, запустите, проверьте health, вход/выход панели, Basic API, S3 PUT/GET и локальные реплики. В кластере заранее остановите записи на время обновления; поочерёдный рестарт не гарантирует непрерывную запись. Для отката используйте сохранённый бинарник и при необходимости отдельную резервную копию данных.

- Перенаправление на форму/`401`: сеанс отсутствует или истёк; войдите с ADMIN_USER / ADMIN_PASSWORD либо общей парой, если отдельный администратор не настроен.
- `403 CSRF token required`: обновите страницу панели и повторите действие; автоматизация должна использовать Basic/SigV4 без browser cookie.
- `503 audit unavailable`: проверьте свободное место и доступность журнала, операция не началась.
- `401` на `/internal/*`: неверный CLUSTER_TOKEN или секреты узлов различаются.
- `SignatureDoesNotMatch`: проверьте REGION, ключи, часы, неизменность Host/пути/query на proxy.
- `413 EntityTooLarge`: превышен MAX_OBJECT_SIZE; проверьте также лимит proxy.
- `507 InsufficientStorage`: проверьте квоту, свободный резерв и общий бюджет временных загрузок. Существующие объекты остаются доступны; освободите место/дождитесь завершения параллельных загрузок и повторите запрос.
- `InvalidObjectState`: файл или метаданные не проходят проверку; сравните с независимой копией и восстановите данные, не отключая проверку для сокрытия ошибки.
- `503`: посмотрите доступность primary/реплик, токен, TLS и журналы; операция могла примениться частично.
- `BucketNotEmpty`: удалите все объекты, проверьте незавершённые операции и локальные списки узлов.
- Ошибка запуска: проверьте синтаксис env, права DATA_ROOT/журнала аудита, пару TLS-файлов, NODE_ID и число узлов для RF.

Расширенный перечень незавершённых возможностей: [STATUS.md](STATUS.md).

## Проверка сборки панели и сценариев восстановления

Скомпилированный Tailwind CSS включён в репозиторий и бинарник: `make build` и запуск не требуют Node.js или доступа к CDN. Для изменения оформления нужны Node.js 22+ и npm:

```bash
make ui
make build
```

CSS-источник — `web/styles.css`, разметка и скрипт — `internal/webui/static/`. Версии Tailwind/CLI и транзитивных пакетов закреплены в package-lock.json. CI пересобирает CSS и сравнивает результат с сохранённым.

```bash
go test -race ./...
go vet ./...
make build
python3 scripts/smoke.py --binary ./bin/kladovka
python3 scripts/smoke.py --binary ./bin/kladovka --access-policy
python3 scripts/consensus_smoke.py --binary ./bin/kladovka
```

S3 smoke требует AWS CLI и работает только со своими временными DATA_ROOT: проверяет multipart, Range, presigned GET и остановку/копирование/восстановление с SHA-256. Consensus smoke дополнительно проверяет failover, замену потерянного участника, переход состава 3→4→5→4→3, полный рестарт, метрики и отказ меньшинства. Тесты storage дополнительно завершают дочерний процесс без cleanup на трёх этапах записи/удаления и проверяют replay при новом запуске. Эти проверки не являются испытанием реального отключения питания или гарантией оборудования.


Замена consensus-участника при потере диска выполняется через нового неголосующего кандидата и административный API; подробная процедура — [CONSENSUS.md, раздел 8](CONSENSUS.md#8-замена-потерянного-узла-новым-сервером). Не используйте legacy-миграцию или повторный bootstrap для этой операции.


Проверенные версии AWS CLI, boto3 и MinIO Python SDK, настройки и границы поддержки описаны в [S3_CLIENTS.md](S3_CLIENTS.md). Контрактные проверки добавлены после v0.4.0; исправлено повторное URL-декодирование ключей с `%`.


### Эксплуатация CopyObject (после v0.4.0)

[Профиль API](USER.md#copyobject-после-v040) использует общий лимит MAX_CONCURRENT_UPLOADS, MAX_OBJECT_SIZE, MAX_TEMP_BYTES, минимального свободного места и квоты. Во время копирования хранится временный файл на DATA_ROOT; объём RAM не растёт пропорционально объекту. Учитывайте место для промежуточных файлов и долговременной записи, как при PUT.

В consensus запрос с follower пересылается лидеру. Источник закрепляется на прочитанном подтверждённом поколении, назначение записывается обычным кворумным путём. Maintenance drain учитывает копирование как активный HTTP-запрос. Это не обещает атомарную транзакцию над двумя ключами при конкурентных изменениях.

В legacy запрос выполняет primary **назначения**. Если primary источника другой, сервер читает его через защищённый internal API, сверяет SHA-256 и затем реплицирует назначение. Локальная устаревшая реплика не используется как замена primary. Недоступность исходного primary возвращает ошибку; failover legacy этим не добавляется. Перед использованием CopyObject обновите все legacy-узлы: для проверки удалённого источника требуется новый внутренний заголовок X-Kladovka-Sha256. Со старым узлом операция завершится ошибкой проверки целостности.

Успешные копии видны как операция CopyObject в метриках S3; переданные внутри сервера байты не учитываются как клиентская загрузка. Аудит фиксирует пользователя, метод PUT, путь назначения и результат; отдельное поле исходного ключа пока не сохраняется. Ошибка репликации после локальной публикации — 503 и возможное уже изменённое назначение: проверяйте результат перед повтором. Резервное копирование этим API не заменяется.
