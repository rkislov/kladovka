# Инструкция администратора

Актуализировано 19 октября 2026 года. Инструкция соответствует коду в этой рабочей копии; старые релизные бинарники могут иметь другой набор функций. Возможности и ограничения перечислены в [состоянии проекта](STATUS.md).

## 1. Назначение и границы

Кладовка — файловое объектное хранилище с частью path-style S3 API и встроенной панелью. Один процесс обслуживает один DATA_ROOT. Запуск нескольких процессов с одним каталогом данных не поддерживается.

Рекомендуемый начальный режим — один узел в доверенной сети с HTTPS и резервным копированием. Кластер поддерживает синхронное копирование, но пока не имеет автоматического перевыбора primary, восстановления пропущенных копий и переноса данных при изменении состава. Не меняйте состав рабочего кластера без плана миграции.

## 2. Сборка и пробный запуск

Нужны Go 1.25+ и make. Внешние Go-зависимости отсутствуют.

```bash
make build
make test
./bin/kladovka -version
```

Для локального запуска создайте отдельный каталог и задайте свои реквизиты:

```bash
export LISTEN_ADDR=127.0.0.1:8000
export DATA_ROOT="$PWD/data"
export NODE_URL=http://127.0.0.1:8000
export ACCESS_KEY=admin
# Введите секрет; значение не записывается в историю команд.
read -r -s SECRET_KEY
export SECRET_KEY
export MAX_OBJECT_SIZE=1073741824
./bin/kladovka
```

Откройте `/ui/` и введите ACCESS_KEY как имя пользователя, SECRET_KEY как пароль. Через HTTP такой вход допустим только на локальной машине или в защищённом туннеле. На сервере используйте HTTPS.

Проверки из другого терминала (задайте там те же переменные):

```bash
curl --fail http://127.0.0.1:8000/healthz
curl --fail --user "$ACCESS_KEY:$SECRET_KEY" http://127.0.0.1:8000/api/stats
```

## 3. Конфигурация

Конфигурация читается при старте. Для изменения перезапустите процесс.

- `LISTEN_ADDR`: адрес прослушивания, по умолчанию `:8000`. Для локального запуска задавайте `127.0.0.1:8000`.
- `DATA_ROOT`: каталог данных, по умолчанию `./data`. В службе задавайте абсолютный путь.
- `ACCESS_KEY`, `SECRET_KEY`: одна общая пара доступа к S3 и панели. Значения по умолчанию `kladovka` / `kladovka-secret` предназначены для знакомства; перед эксплуатацией замените их.
- `REGION`: регион подписи, по умолчанию `us-east-1`; должен совпадать у клиента и сервера.
- `NODE_ID`: идентификатор узла, по умолчанию `node-1`. В кластере обязан совпадать с `host:port` в NODE_URL.
- `NODE_URL`: базовый HTTP(S) URL без пути и query, по умолчанию `http://localhost:8000`. Должен быть доступен остальным узлам и Prometheus.
- `PEER_NODES`: базовые URL остальных узлов через запятую, без собственного узла и повторов. По умолчанию пусто.
- `REPLICATION_FACTOR`: число копий с учётом primary, по умолчанию `1`; не больше числа настроенных узлов.
- `CLUSTER_TOKEN`: общий секрет межнодового API. Задавайте одинаковое случайное значение на всех узлах. Если не задан, токен выводится из SECRET_KEY; для Prometheus SD удобнее задать явно.
- `CLUSTER_VERIFY_TLS`: проверять сертификаты пиров, по умолчанию `true`. `false` допустимо только в лаборатории.
- `HEALTH_INTERVAL_SEC`: интервал проверки пиров в секундах, по умолчанию `10`, строго больше нуля. Один health-запрос ограничен тремя секундами.
- `MAX_OBJECT_SIZE`: максимальный размер объекта в байтах; `0` — без настроенного лимита. Применяется к обычным, внутренним и multipart-загрузкам, включая собранный объект. Выберите лимит по доступному месту, нагрузке и времени передачи.
- `TLS_CERT_FILE`, `TLS_KEY_FILE`: оба пути к PEM-файлам; задаются вместе. Без них сервер работает по HTTP.
- `TLS_MIN_VERSION`: `1.2` (по умолчанию) или `1.3`.

Загрузка использует временный файл ОС, затем запись в DATA_ROOT. Для крупных объектов предусмотрите запас места на обоих томах; `TMPDIR` можно направить на подходящий диск. Части незавершённых multipart лежат в DATA_ROOT/.multipart и также занимают место. Данные не буферизуются целиком в оперативной памяти при обычном PUT.

## 4. Установка на Linux с systemd

Создайте системного пользователя `kladovka` штатным инструментом дистрибутива, без интерактивного входа. Затем:

```bash
sudo install -m 0755 ./bin/kladovka /usr/local/bin/kladovka
sudo install -d -o kladovka -g kladovka -m 0700 /var/lib/kladovka
sudo install -d -m 0750 /etc/kladovka
sudo install -m 0600 /dev/null /etc/kladovka/kladovka.env
sudoedit /etc/kladovka/kladovka.env
```

Содержимое env-файла (замените оба секрета):

```ini
LISTEN_ADDR=127.0.0.1:8000
DATA_ROOT=/var/lib/kladovka
NODE_ID=node-1
NODE_URL=http://127.0.0.1:8000
ACCESS_KEY=admin
SECRET_KEY=REPLACE_WITH_RANDOM_SECRET
CLUSTER_TOKEN=REPLACE_WITH_ANOTHER_RANDOM_SECRET
REGION=us-east-1
REPLICATION_FACTOR=1
MAX_OBJECT_SIZE=1073741824
```

Пример `/etc/systemd/system/kladovka.service`:

```ini
[Unit]
Description=Kladovka object storage
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=kladovka
Group=kladovka
EnvironmentFile=/etc/kladovka/kladovka.env
WorkingDirectory=/var/lib/kladovka
ExecStart=/usr/local/bin/kladovka
Restart=on-failure
RestartSec=3
TimeoutStopSec=40
UMask=0077
NoNewPrivileges=true
PrivateTmp=true
ProtectHome=true
ProtectSystem=strict
ReadWritePaths=/var/lib/kladovka

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now kladovka
sudo systemctl status kladovka
sudo journalctl -u kladovka -n 100 --no-pager
```

При SIGTERM сервер прекращает приём новых соединений и ждёт активные запросы до 30 секунд. Перед остановкой для резервного копирования сначала прекратите записи со стороны клиентов; запрос, не уложившийся в срок, может быть прерван.

## 5. HTTPS и доступ

Для прямого HTTPS добавьте в env-файл:

```ini
LISTEN_ADDR=:8443
NODE_URL=https://storage.example.org:8443
TLS_CERT_FILE=/etc/kladovka/tls/fullchain.pem
TLS_KEY_FILE=/etc/kladovka/tls/key.pem
TLS_MIN_VERSION=1.2
```

Пользователь службы должен читать сертификат и ключ. Приватный ключ не публикуйте. После обновления сертификата перезапустите службу.

Маршруты имеют разную авторизацию:

- S3 (`/`, `/<полка>`, `/<полка>/<ключ>`): AWS SigV4 или presigned URL.
- `/ui/`, `/api/*`, `/cluster`, `/metrics`: HTTP Basic с ACCESS_KEY / SECRET_KEY.
- `/internal/*`: `Authorization: Bearer <CLUSTER_TOKEN>`; ограничьте доступ также сетью.
- `/healthz`: публичная проверка живого процесса; не подтверждает исправность репликации или доступность записи на диск.

Basic-вход не создаёт отдельную учётную запись или роль. Все обладатели этой пары могут читать, изменять и удалять данные. IAM, ACL и многопользовательского разграничения пока нет.

При reverse proxy сохраняйте исходный Host, путь и query для SigV4. Не добавляйте Basic-авторизацию на S3-маршруты и не заменяйте заголовок Authorization клиента. Ограничьте публичный доступ к внутренним маршрутам, настройте лимиты тела и тайм-ауты передачи на proxy. Используйте собственный CA через доверенное системное хранилище, а не отключение проверки TLS.

## 6. Два узла

На обоих узлах используйте одну пару ACCESS_KEY / SECRET_KEY, один REGION, один CLUSTER_TOKEN, RF=2 и разные локальные каталоги данных.

Узел A:

```ini
LISTEN_ADDR=:8000
NODE_ID=10.0.0.10:8000
NODE_URL=http://10.0.0.10:8000
PEER_NODES=http://10.0.0.11:8000
REPLICATION_FACTOR=2
```

Узел B:

```ini
LISTEN_ADDR=:8000
NODE_ID=10.0.0.11:8000
NODE_URL=http://10.0.0.11:8000
PEER_NODES=http://10.0.0.10:8000
REPLICATION_FACTOR=2
```

Эти HTTP-адреса — пример для изолированной лабораторной сети. На рабочей сети настройте HTTPS и доверенные сертификаты.

Запустите оба узла, затем создавайте полки. Создание и удаление полок передаются остальным настроенным узлам. Согласованность этих операций не транзакционная: при отказе возможен частичный результат; после восстановления повторите операцию через S3 API.

PUT/DELETE и multipart направляются на primary по хешу ключа; подпись клиента сохраняет исходный Host. PUT и завершение multipart успешны только после подтверждения текущих реплик. При ошибке копирования возвращается 503; локальный объект уже может существовать. Повторяйте тот же PUT или CompleteMultipartUpload после восстановления связи. Части multipart сохраняются до успешной репликации. DELETE также может выполниться частично, и тогда его нужно повторить.

GET/HEAD пробуют реплики при отсутствии локального объекта. При недоступном primary записи не переключаются автоматически. Успешная предыдущая запись не запускает фоновое восстановление, если позже потерян диск. Периодически проверяйте независимые резервные копии. Состав и сортировка NODE_ID участвуют в размещении; это хеширование по модулю количества узлов, без автоматического ребаланса.

Статистика и списки объектов относятся к текущей ноде, а не являются глобальным каталогом. При RF меньше числа узлов разные ноды могут показывать разные объекты. Метка `healthy` означает успешный health HTTP-запрос, а не проверку контрольных сумм данных.

## 7. Мониторинг

В панели смотрите счётчики операций, трафик, состояние узлов и ошибки репликации. Счётчики и uptime сбрасываются при рестарте. Диск показывает всю файловую систему DATA_ROOT; размеры объектов показывают только локальные объекты без sidecar и multipart-частей.

Пример Prometheus: [monitoring/prometheus.yml](../monitoring/prometheus.yml). Замените endpoint, Basic username и пути к файлам секретов. В `kladovka-secret` хранится SECRET_KEY, в `kladovka-cluster-token` — явно заданный CLUSTER_TOKEN; оба файла должны быть доступны только Prometheus и администратору. Для HTTPS используйте HTTPS URL SD и доверенный CA.

Следите за `up`, `kladovka_cluster_node_healthy`, ростом `kladovka_replication_failed_total`, свободным местом файловой системы, HTTP 5xx и временем ответа. `/metrics` и `/api/stats` не заменяют проверку чтения контрольного объекта. HTTP-счётчик растёт и от опросов панели.

## 8. Резервное копирование и восстановление

1. Остановите поступление новых записей, дождитесь завершения загрузок.
2. Остановите службу: `sudo systemctl stop kladovka`.
3. Скопируйте весь DATA_ROOT вместе со скрытыми каталогами и файлами `*.kladovka-meta.json`. В кластере сделайте согласованные копии всех узлов.
4. Отдельно сохраните env-файл, TLS-материалы и версию бинарника в защищённое хранилище.
5. Запустите службу и проверьте чтение контрольного объекта.

Пример копирования на отдельный том при остановленной службе:

```bash
sudo rsync -a /var/lib/kladovka/ /mnt/backup/kladovka/
```

При восстановлении остановите службу, восстановите каталог в отдельный пустой DATA_ROOT, верните владельца `kladovka:kladovka`, конфигурацию и совместимую версию бинарника. Запустите службу, проверьте список и скачивание файлов с контрольными суммами. Не проверяйте восстановление поверх единственной рабочей копии.

Не редактируйте файлы объектов и метаданные вручную при работающем процессе. Не очищайте `.multipart` во время загрузок. Автоматического удаления старых незавершённых загрузок пока нет; отменяйте известный upload через S3 AbortMultipartUpload.

## 9. Обновление и диагностика

Перед обновлением сделайте резервную копию и проверьте новую сборку на копии данных. Остановите службу, замените бинарник, запустите, проверьте health, Basic-вход, S3 PUT/GET и репликацию. Для отката используйте сохранённый бинарник и при необходимости отдельную резервную копию данных.

- `401` на панели: нужны Basic-реквизиты, совпадающие с ACCESS_KEY / SECRET_KEY.
- `401` на `/internal/*`: неверный CLUSTER_TOKEN или секреты узлов различаются.
- `SignatureDoesNotMatch`: проверьте REGION, ключи, часы, неизменность Host/пути/query на proxy.
- `413 EntityTooLarge`: превышен MAX_OBJECT_SIZE; проверьте также лимит proxy.
- `503`: посмотрите доступность primary/реплик, токен, TLS и журналы; операция могла примениться частично.
- `BucketNotEmpty`: удалите все объекты, проверьте незавершённые операции и локальные списки узлов.
- Ошибка запуска: проверьте синтаксис env, права DATA_ROOT/TMPDIR, пару TLS-файлов, NODE_ID и число узлов для RF.

Расширенный перечень незавершённых возможностей: [STATUS.md](STATUS.md).
