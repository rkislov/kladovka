# Инструкция администратора

Актуализировано 20 октября 2026 года. Рабочая версия: 0.4.0-dev (поверх релиза v0.3.0). Инструкция соответствует коду в этой рабочей копии; старые релизные бинарники могут иметь другой набор функций. Возможности и ограничения перечислены в [состоянии проекта](STATUS.md).

## 1. Назначение и границы

Кладовка — файловое объектное хранилище с частью path-style S3 API и встроенной панелью. Один процесс обслуживает один DATA_ROOT. Запуск нескольких процессов с одним каталогом данных не поддерживается.

Рекомендуемый начальный режим — один узел в доверенной сети с HTTPS и резервным копированием. Кластер поддерживает синхронное копирование, но пока не имеет автоматического перевыбора primary, восстановления пропущенных копий и переноса данных при изменении состава. Не меняйте состав рабочего кластера без плана миграции.

## 2. Сборка и пробный запуск

Нужны Go 1.25+ и make. Внешние Go-зависимости отсутствуют.

```bash
make build
make test
./bin/kladovka -version
```

Для локального запуска создайте отдельный каталог и задайте свои реквизиты:

```bash
export LISTEN_ADDR=127.0.0.1:8000
export DATA_ROOT="$PWD/data"
export NODE_URL=http://127.0.0.1:8000
export ACCESS_KEY=admin
# Введите секрет; значение не записывается в историю команд.
read -r -s SECRET_KEY
export SECRET_KEY
export MAX_OBJECT_SIZE=1073741824
./bin/kladovka
```

Откройте `/ui/`: появится форма входа. Введите ADMIN_USER / ADMIN_PASSWORD, если они заданы; иначе ACCESS_KEY / SECRET_KEY. После входа панель создаёт ограниченный по времени сеанс; кнопка «Выйти» отзывает его. Через HTTP такой вход допустим только на локальной машине или в защищённом туннеле. На сервере используйте HTTPS.

Проверки из другого терминала (задайте там те же переменные):

```bash
curl --fail http://127.0.0.1:8000/healthz
curl --fail --user "$ACCESS_KEY:$SECRET_KEY" http://127.0.0.1:8000/api/stats
```

## 3. Конфигурация

Конфигурация читается при старте. Для изменения перезапустите процесс.

- `LISTEN_ADDR`: адрес прослушивания, по умолчанию `:8000`. Для локального запуска задавайте `127.0.0.1:8000`.
- `DATA_ROOT`: каталог данных, по умолчанию `./data`. В службе задавайте абсолютный путь.
- `ACCESS_KEY`, `SECRET_KEY`: общая пара доступа к S3 и панели в режиме совместимости без файла доступа и отдельных Basic-реквизитов. Значения по умолчанию `kladovka` / `kladovka-secret` предназначены для знакомства; перед эксплуатацией замените их.
- `REGION`: регион подписи, по умолчанию `us-east-1`; должен совпадать у клиента и сервера.
- `NODE_ID`: идентификатор узла, по умолчанию `node-1`. В кластере обязан совпадать с `host:port` в NODE_URL.
- `NODE_URL`: базовый HTTP(S) URL без пути и query, по умолчанию `http://localhost:8000`. Должен быть доступен остальным узлам и Prometheus.
- `PEER_NODES`: базовые URL остальных узлов через запятую, без собственного узла и повторов. По умолчанию пусто.
- `REPLICATION_FACTOR`: число копий с учётом primary, по умолчанию `1`; не больше числа настроенных узлов.
- `CLUSTER_TOKEN`: общий секрет межнодового API. Задавайте одинаковое случайное значение на всех узлах. Если не задан, токен выводится из SECRET_KEY; для Prometheus SD удобнее задать явно.
- `CLUSTER_VERIFY_TLS`: проверять сертификаты пиров, по умолчанию `true`. `false` допустимо только в лаборатории.
- `HEALTH_INTERVAL_SEC`: интервал проверки пиров в секундах, по умолчанию `10`, строго больше нуля. Один health-запрос ограничен тремя секундами.
- `MAX_CONCURRENT_UPLOADS`: число одновременных локальных загрузок, по умолчанию `4`, диапазон 1–1024. При заполнении возвращается 503 с Retry-After. Чтение и статистика не занимают эти слоты; пересылка на другой primary также не занимает локальный слот.
- `MAX_TEMP_BYTES`: общий бюджет одновременно принимаемых временных тел на узле, по умолчанию 2147483648 (2 GiB), `0` отключает бюджет. Превышение даёт 507. Для одиночного обычного PUT этот бюджет тоже ограничивает размер файла.
- `STORAGE_QUOTA_BYTES`: квота суммарного содержимого объектов и multipart-частей на узле, по умолчанию `0` (без квоты). Метаданные не входят в логическую квоту. Для перезаписи и сборки multipart нужен запас под новое содержимое рядом со старым/частями; превышение возвращает 507 и не публикует частичный объект.
- `MIN_FREE_DISK_BYTES`: свободный резерв файловой системы DATA_ROOT, по умолчанию 67108864 (64 MiB), `0` отключает. Перед порциями записи проверяется доступное место; при достижении резерва возвращается 507. Это не резервирование места против сторонних процессов ОС.
- `VERIFY_OBJECT_CHECKSUM`: проверять контрольную сумму перед выдачей объекта, по умолчанию `true`. Для новых объектов сохраняется SHA-256; повреждение блокирует чтение с InvalidObjectState. Проверка полностью читает файл перед выдачей, в том числе для HEAD/Range, и увеличивает дисковую нагрузку. Отключение `false` уменьшает эту проверку, но не даёт той же защиты чтения.
- `MULTIPART_TTL_SEC`: срок без изменения multipart-загрузки, по умолчанию 86400 (24 часа), строго положительный. Свежие части обновляют время; активный HTTP-запрос, включая завершение/репликацию, защищён от TTL-очистки.
- `CLEANUP_INTERVAL_SEC`: период TTL-очистки, по умолчанию 600 секунд, строго положительный. Очистка также выполняется при старте.
- `MAX_OBJECT_SIZE`: максимальный размер объекта в байтах; `0` — без настроенного лимита. Применяется к обычным, внутренним и multipart-загрузкам, включая собранный объект. Выберите лимит по доступному месту, нагрузке и времени передачи.
- `TLS_CERT_FILE`, `TLS_KEY_FILE`: оба пути к PEM-файлам; задаются вместе. Без них сервер работает по HTTP.
- `TLS_MIN_VERSION`: `1.2` (по умолчанию) или `1.3`.

Загрузка использует DATA_ROOT/.uploads, затем журнал DATA_ROOT/.transactions и окончательный файл. Для крупных объектов предусмотрите запас места под принимаемое тело и новую копию одновременно; multipart при сборке требует место под части и полный результат. TMPDIR больше не определяет место приёма HTTP-тел. Оставшиеся после аварии upload-*.tmp очищаются при запуске. Части multipart находятся в DATA_ROOT/.multipart. Обычный PUT не буферизуется целиком в RAM.

При запуске сервер сначала восстанавливает подготовленные записи и удаления из `.transactions`, затем начинает обслуживать запросы. Журнал и SHA-256 метаданных синхронизируются перед публикацией; каталоги синхронизируются после rename/delete. Если публикация пары «объект + метаданные» оборвалась, чтение этого ключа блокируется до успешного восстановления. Неподтверждённый запрос после сбоя мог примениться — проверяйте объект или повторяйте запрос. В одном узле PUT/DELETE и публикация метаданных упорядочены; это не решает согласование конкурентных записей между узлами.

Не удаляйте `.transactions` вручную. Если запуск сообщает ошибку восстановления, освободите место/восстановите права и сохраните резервную копию журнала прежде, чем предпринимать исправления. Старые версии не умеют восстанавливать новый журнал: откат бинарника допускается только после завершения всех записей, остановки службы и проверки пустого журнала либо на совместимую резервную копию.

При первом запуске на каталоге v0.3 сервер один раз проходит существующие объекты, проверяет обычные MD5 ETag, дополняет метаданные SHA-256 и сохраняет скрытый маркер формата. Это может занять время на большом хранилище; делайте переход в окно обслуживания и после резервной копии. Старые multipart-объекты или legacy-файлы без метаданных получают исходную SHA-256 по текущим байтам — это не доказывает их целостность до обновления. После перехода отсутствие/повреждение метаданных блокирует чтение, а не отключает проверку незаметно. Сохраняйте маркер формата в резервной копии.

## 4. Установка на Linux с systemd

Создайте системного пользователя `kladovka` штатным инструментом дистрибутива, без интерактивного входа. Затем:

```bash
sudo install -m 0755 ./bin/kladovka /usr/local/bin/kladovka
sudo install -d -o kladovka -g kladovka -m 0700 /var/lib/kladovka
sudo install -d -m 0750 /etc/kladovka
sudo install -m 0600 /dev/null /etc/kladovka/kladovka.env
sudoedit /etc/kladovka/kladovka.env
```

Содержимое env-файла (замените оба секрета):

```ini
LISTEN_ADDR=127.0.0.1:8000
DATA_ROOT=/var/lib/kladovka
NODE_ID=node-1
NODE_URL=http://127.0.0.1:8000
ACCESS_KEY=admin
SECRET_KEY=REPLACE_WITH_RANDOM_SECRET
CLUSTER_TOKEN=REPLACE_WITH_ANOTHER_RANDOM_SECRET
REGION=us-east-1
REPLICATION_FACTOR=1
MAX_OBJECT_SIZE=1073741824
```

Пример `/etc/systemd/system/kladovka.service`:

```ini
[Unit]
Description=Kladovka object storage
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=kladovka
Group=kladovka
EnvironmentFile=/etc/kladovka/kladovka.env
WorkingDirectory=/var/lib/kladovka
ExecStart=/usr/local/bin/kladovka
Restart=on-failure
RestartSec=3
TimeoutStopSec=40
UMask=0077
NoNewPrivileges=true
PrivateTmp=true
ProtectHome=true
ProtectSystem=strict
ReadWritePaths=/var/lib/kladovka

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now kladovka
sudo systemctl status kladovka
sudo journalctl -u kladovka -n 100 --no-pager
```

При SIGTERM сервер прекращает приём новых соединений и ждёт активные запросы до 30 секунд. Перед остановкой для резервного копирования сначала прекратите записи со стороны клиентов; запрос, не уложившийся в срок, может быть прерван.

## 5. HTTPS и доступ

Для прямого HTTPS добавьте в env-файл:

```ini
LISTEN_ADDR=:8443
NODE_URL=https://storage.example.org:8443
TLS_CERT_FILE=/etc/kladovka/tls/fullchain.pem
TLS_KEY_FILE=/etc/kladovka/tls/key.pem
TLS_MIN_VERSION=1.2
```

Пользователь службы должен читать сертификат и ключ. Приватный ключ не публикуйте. После обновления сертификата перезапустите службу.

Маршруты имеют разную авторизацию:

- S3 (`/`, `/<полка>`, `/<полка>/<ключ>`): AWS SigV4 или presigned URL.
- `/ui/`: сеанс администратора, вход через форму `/ui/login.html`. Без сеанса панель перенаправляет на форму; Basic больше не открывает панель. Форма, её JS и CSS публичны и не содержат данных хранилища.
- `/api/*`, `/cluster`, `/metrics`: сеанс панели либо HTTP Basic с ADMIN_USER / ADMIN_PASSWORD (если заданы), иначе ACCESS_KEY / SECRET_KEY. JSON API также принимает SigV4 с ролями пользователя; полная статистика доступна только admin.
- `/api/session`: POST создаёт сеанс по JSON `user`/`password`, GET возвращает пользователя, срок и CSRF-токен, DELETE завершает сеанс с `X-CSRF-Token`. Basic/SigV4 не заменяют сеанс на этом маршруте.
- `/internal/*`: `Authorization: Bearer <CLUSTER_TOKEN>`; ограничьте доступ также сетью.
- `/healthz`: публичная проверка живого процесса; не подтверждает исправность репликации или доступность записи на диск.

Вход в панель и Basic API предоставляют полный доступ администратора. S3-ключи пользователей из файла доступа не принимаются как реквизиты панели. AWS IAM/ACL и персональные учётные записи панели для reader/writer пока отсутствуют.

При reverse proxy сохраняйте исходный Host, путь и query для SigV4. Не добавляйте Basic-авторизацию на S3-маршруты и не заменяйте заголовок Authorization клиента. Ограничьте публичный доступ к внутренним маршрутам, настройте лимиты тела и тайм-ауты передачи на proxy. Используйте собственный CA через доверенное системное хранилище, а не отключение проверки TLS.

### Сеансы панели

`SESSION_TTL_SEC` задаёт абсолютный срок сеанса: по умолчанию 28800 секунд (8 часов), допустимо 60–86400. Активность срок не продлевает. Сеансы хранятся только в памяти узла, максимум 1024; выход отзывает текущий токен, повторный вход заменяет старый токен этого браузера, перезапуск отзывает все сеансы узла. Изменение реквизитов администратора также делает старые сеансы недействительными. На другом узле требуется отдельный вход. Для пересылки записи на primary сервер использует административные Basic-реквизиты, не передавая cookie или CSRF-токен браузера; реквизиты должны совпадать на узлах.

Cookie имеет HttpOnly, SameSite=Strict, Path=/ и не сохраняется в localStorage. Secure включается при TLS или HTTPS в NODE_URL. За HTTPS reverse proxy задавайте внешний HTTPS NODE_URL и сохраняйте Host; произвольным X-Forwarded-* сервер не доверяет. Для изменяющих запросов с cookie требуется `X-CSRF-Token`, а Origin проверяется по схеме и Host. Basic и SigV4 остаются для автоматизации без cookie; не смешивайте их с cookie просроченного сеанса. Срок/ошибки сеанса не дают автоматического перехода к общей паре ключей.

Вход принимает только JSON, ограничен десятью попытками в минуту с одного сетевого адреса. За proxy этот лимит общий для его адреса: предусмотрите отдельные ограничения и правильную сетевую схему. Число адресов в памяти ограничено 4096. Секреты входа не возвращаются в ответе и не попадают в аудит. После выхода ранее начатая передача может завершиться; Basic API-реквизиты не отзываются кнопкой выхода и должны оставаться у автоматизации/администратора.

### Журнал аудита

По умолчанию журнал — `DATA_ROOT/.audit.jsonl`, права 0600. `AUDIT_LOG_FILE` позволяет выбрать отдельный файл вне DATA_ROOT; его родительский каталог должен существовать и быть доступен службе. Размещать журнал среди объектов полок нельзя. При старте недоступный или открытый другим пользователям файл не принимается. Журнал содержит имена пользователей, ключей доступа и объектов; защищайте его и резервные копии как служебные данные.

Для изменяющих HTTP-запросов записываются `attempt` до обработки и `result` с проверенным пользователем (`actor`), методом, путём, HTTP-статусом и общим `request_id`. Каждая запись синхронизируется на диск. Пароли, Secret Key, Authorization, cookies, CSRF-токены, query подписанных ссылок и тела запросов не журналируются. Внутренние запросы реплик помечаются `cluster`; исходный пользователь фиксируется на входном узле. При недоступности предварительной записи операция возвращает 503 и не начинается. Ошибка записи результата не отменяет уже выполненную операцию: она попадает в служебный лог; дальнейшие изменения блокируются до устранения причины и перезапуска. Попытка может остаться без результата и при аварии. Аудит не является транзакцией с хранилищем и не защищён от изменения владельцем файлов.

`policy_snapshot` фиксирует начальную и каждую замеченную новую конфигурацию пользователей, ролей и идентификаторов ключей; Secret Key не записываются даже при ротации. На старте также фиксируется `admin_configuration`. Источник этих изменений — `local_configuration`: сервер не устанавливает, какой человек редактировал файл или environment; для этого нужен аудит ОС. Изменение файла обнаруживается при следующем подписанном запросе или запуске. Пока конфигурация не прочитана, промежуточные правки файла не фиксируются.

Просмотр последних событий: `tail -n 50 /путь/к/.audit.jsonl`. Для ротации остановите службу, перенесите журнал в защищённый архив и запустите службу: она создаст новый файл. Ограничивайте срок хранения и следите за свободным местом; автоматической ротации нет, служебный журнал не входит в квоту объектов. При восстановлении аудит из копии сохраняет исторические события; новые добавляются в конец. После прерванной записи неполная JSON-строка отделяется новой строкой; при разборе старого хвоста учитывайте это.

### Пользователи и ключи

Для разграничения доступа задайте `ACCESS_POLICY_FILE=/etc/kladovka/access.json`, отдельные `ADMIN_USER` и `ADMIN_PASSWORD` (не менее 16 байт), а также явный `CLUSTER_TOKEN`. Basic-реквизиты администратора задаются вместе; без файла доступа их тоже можно отделить от общей S3-пары. Передавайте секреты через защищённый environment-файл службы.

Файл доступа должен быть обычным файлом размером не более 1 MiB и с правами `0600` (доступен владельцу службы). Храните его вне DATA_ROOT и Git. Пример структуры с демонстрационными секретами, которые необходимо заменить:

```json
{
  "version": 1,
  "users": [
    {
      "id": "backup-reader",
      "role": "reader",
      "polki": ["backups"],
      "keys": [
        {"access_key": "backup-reader-1", "secret_key": "REPLACE-WITH-RANDOM-SECRET-1"},
        {"access_key": "backup-reader-2", "secret_key": "REPLACE-WITH-RANDOM-SECRET-2"}
      ]
    },
    {
      "id": "photo-uploader",
      "role": "writer",
      "polki": ["photos"],
      "keys": [{"access_key": "photo-uploader-1", "secret_key": "REPLACE-WITH-RANDOM-SECRET-3"}]
    }
  ]
}
```

Роль `reader` разрешает LIST/GET/HEAD существующих объектов в перечисленных полках. `writer` дополнительно разрешает PUT/DELETE объектов и все операции multipart в этих полках. Это доступ ко всей полке, включая multipart других писателей этой полки. Создавать и удалять полки может только `admin`. Роль `admin` в файле даёт S3-клиенту полный доступ ко всем полкам и JSON API; пароль панели она не создаёт. Подстановок и наследования имён полок нет. Список полок через S3 и JSON фильтруется по правам; статистика всего узла, метрики и панель остаются административными. Полки заранее создаёт администратор.

ID пользователей и Access Key должны быть уникальны во всём файле; у пользователя может быть несколько ключей или ни одного. Secret Key должен содержать не менее 16 байт; для рабочих ключей используйте длинные случайные значения. Секреты хранятся в файле открытым текстом, поскольку нужны для проверки SigV4, поэтому защищайте файл и его резервные копии.

При заданном ACCESS_POLICY_FILE общая S3-пара ACCESS_KEY / SECRET_KEY отключается. Файл проверяется при старте и заново для каждого подписанного запроса. Для выдачи/отзыва ключа или изменения роли подготовьте полный новый файл с правами 0600 рядом с действующим и замените его атомарным rename, например `mv /etc/kladovka/access.new /etc/kladovka/access.json`, сохранив владельца службы. Удаление записи ключа отзывает также его presigned URL на новых запросах. Уже выполняющаяся передача может завершиться с ранее проверенными правами. Ошибочный, отсутствующий или слишком открытый файл блокирует подписанный доступ; возврата к общей паре и старому снимку нет. административный доступ администратора остаётся для восстановления конфигурации. Смена Basic-реквизитов требует перезапуска службы.

Не редактируйте файл на месте: частично записанный JSON временно блокирует доступ. На всех узлах кластера установите одинаковые файлы доступа и Basic-реквизиты; централизованной доставки и атомарного отзыва сразу на всех узлах пока нет. До обновления последнего узла старые ключи на нём действуют. Резервируйте конфигурацию доступа отдельно от данных и не восстанавливайте отозванные ключи из старой копии без проверки.

## 6. Два узла

На обоих узлах используйте одинаковую конфигурацию доступа (файлы политик и Basic-реквизиты либо общую пару ACCESS_KEY / SECRET_KEY), один REGION, один CLUSTER_TOKEN, RF=2 и разные локальные каталоги данных.

Узел A:

```ini
LISTEN_ADDR=:8000
NODE_ID=10.0.0.10:8000
NODE_URL=http://10.0.0.10:8000
PEER_NODES=http://10.0.0.11:8000
REPLICATION_FACTOR=2
```

Узел B:

```ini
LISTEN_ADDR=:8000
NODE_ID=10.0.0.11:8000
NODE_URL=http://10.0.0.11:8000
PEER_NODES=http://10.0.0.10:8000
REPLICATION_FACTOR=2
```

Эти HTTP-адреса — пример для изолированной лабораторной сети. На рабочей сети настройте HTTPS и доверенные сертификаты.

Запустите оба узла, затем создавайте полки. Создание и удаление полок передаются остальным настроенным узлам. Согласованность этих операций не транзакционная: при отказе возможен частичный результат; после восстановления повторите операцию через S3 API.

PUT/DELETE и multipart направляются на primary по хешу ключа; подпись клиента сохраняет исходный Host. PUT и завершение multipart успешны только после подтверждения текущих реплик. При ошибке копирования возвращается 503; локальный объект уже может существовать. Повторяйте тот же PUT или CompleteMultipartUpload после восстановления связи. Части multipart сохраняются до успешной репликации. DELETE также может выполниться частично, и тогда его нужно повторить.

GET/HEAD пробуют реплики при отсутствии локального объекта. При недоступном primary записи не переключаются автоматически. Успешная предыдущая запись не запускает фоновое восстановление, если позже потерян диск. Периодически проверяйте независимые резервные копии. Состав и сортировка NODE_ID участвуют в размещении; это хеширование по модулю количества узлов, без автоматического ребаланса.

Статистика и списки объектов относятся к текущей ноде, а не являются глобальным каталогом. При RF меньше числа узлов разные ноды могут показывать разные объекты. Метка `healthy` означает успешный health HTTP-запрос, а не проверку контрольных сумм данных.

## 7. Мониторинг

В панели смотрите счётчики операций, трафик, состояние узлов и ошибки репликации. Счётчики и uptime сбрасываются при рестарте. Диск показывает всю файловую систему DATA_ROOT; размеры объектов показывают только локальные объекты без sidecar и multipart-частей.

Пример Prometheus: [monitoring/prometheus.yml](../monitoring/prometheus.yml). Замените endpoint, Basic username и пути к файлам секретов. В `kladovka-secret` хранится ADMIN_PASSWORD (либо SECRET_KEY в режиме общей пары), в `kladovka-cluster-token` — явно заданный CLUSTER_TOKEN; оба файла должны быть доступны только Prometheus и администратору. Для HTTPS используйте HTTPS URL SD и доверенный CA.

Следите за `up`, `kladovka_cluster_node_healthy`, ростом `kladovka_replication_failed_total`, свободным местом файловой системы, HTTP 5xx и временем ответа. `/metrics` и `/api/stats` не заменяют проверку чтения контрольного объекта. HTTP-счётчик растёт и от опросов панели.

## 8. Резервное копирование и восстановление

1. Остановите поступление новых записей, дождитесь завершения загрузок.
2. Остановите службу: `sudo systemctl stop kladovka`.
3. Скопируйте весь DATA_ROOT вместе со скрытыми каталогами, журналом `.transactions`, частями `.multipart` и файлами `*.kladovka-meta.json`. Не копируйте только видимые полки: это потеряет контекст восстановления. В кластере сделайте согласованные копии всех узлов.
4. Отдельно сохраните env-файл, TLS-материалы и версию бинарника в защищённое хранилище.
5. Запустите службу и проверьте чтение контрольного объекта.

Пример копирования на отдельный том при остановленной службе:

```bash
sudo rsync -a /var/lib/kladovka/ /mnt/backup/kladovka/
```

При восстановлении остановите службу, восстановите каталог в отдельный пустой DATA_ROOT, верните владельца `kladovka:kladovka`, конфигурацию и совместимую версию бинарника. Запустите службу, проверьте список и скачивание файлов с контрольными суммами. Не проверяйте восстановление поверх единственной рабочей копии.

Не редактируйте файлы объектов и метаданные вручную при работающем процессе. Не очищайте `.multipart` во время загрузок. Старые неактивные multipart очищаются по TTL. Для немедленной отмены известной загрузки используйте S3 AbortMultipartUpload. Согласуйте TTL с пользователями: он ограничивает срок ручного возобновления после длительного перерыва.

## 9. Обновление и диагностика

Перед обновлением сделайте резервную копию и проверьте новую сборку на копии данных. Остановите службу, замените бинарник, запустите, проверьте health, Basic-вход, S3 PUT/GET и репликацию. Для отката используйте сохранённый бинарник и при необходимости отдельную резервную копию данных.

- Перенаправление на форму/`401`: сеанс отсутствует или истёк; войдите с ADMIN_USER / ADMIN_PASSWORD либо общей парой, если отдельный администратор не настроен.
- `403 CSRF token required`: обновите страницу панели и повторите действие; автоматизация должна использовать Basic/SigV4 без browser cookie.
- `503 audit unavailable`: проверьте свободное место и доступность журнала, операция не началась.
- `401` на `/internal/*`: неверный CLUSTER_TOKEN или секреты узлов различаются.
- `SignatureDoesNotMatch`: проверьте REGION, ключи, часы, неизменность Host/пути/query на proxy.
- `413 EntityTooLarge`: превышен MAX_OBJECT_SIZE; проверьте также лимит proxy.
- `507 InsufficientStorage`: проверьте квоту, свободный резерв и общий бюджет временных загрузок. Существующие объекты остаются доступны; освободите место/дождитесь завершения параллельных загрузок и повторите запрос.
- `InvalidObjectState`: файл или метаданные не проходят проверку; сравните с независимой копией и восстановите данные, не отключая проверку для сокрытия ошибки.
- `503`: посмотрите доступность primary/реплик, токен, TLS и журналы; операция могла примениться частично.
- `BucketNotEmpty`: удалите все объекты, проверьте незавершённые операции и локальные списки узлов.
- Ошибка запуска: проверьте синтаксис env, права DATA_ROOT/TMPDIR, пару TLS-файлов, NODE_ID и число узлов для RF.

Расширенный перечень незавершённых возможностей: [STATUS.md](STATUS.md).

## Проверка сборки панели и сценариев восстановления

Скомпилированный Tailwind CSS включён в репозиторий и бинарник: `make build` и запуск не требуют Node.js или доступа к CDN. Для изменения оформления нужны Node.js 22+ и npm:

```bash
make ui
make build
```

CSS-источник — `web/styles.css`, разметка и скрипт — `internal/webui/static/`. Версии Tailwind/CLI и транзитивных пакетов закреплены в package-lock.json. CI пересобирает CSS и сравнивает результат с сохранённым.

```bash
go test -race ./...
go vet ./...
make build
python3 scripts/smoke.py --binary ./bin/kladovka
```

Последний сценарий требует AWS CLI и работает только со своими временными DATA_ROOT: проверяет автоматический multipart, Range, presigned GET и остановку/копирование/восстановление с проверкой SHA-256. Тесты storage дополнительно завершают дочерний процесс без cleanup на трёх этапах записи/удаления и проверяют replay при новом запуске. Эти проверки не являются испытанием реального отключения питания или гарантией оборудования.
