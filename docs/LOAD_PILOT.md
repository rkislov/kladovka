# Нагрузочный пилот

Сценарий `scripts/load_pilot.py` запускает собственные временные серверы на loopback. Внешний endpoint и существующий DATA_ROOT не принимаются. После завершения процессы останавливаются, временные данные удаляются. Результат сохраняется в новый JSON; существующий файл не перезаписывается. При ошибке после начала прогона сохраняется частичный отчёт со статусом failed и ненулевым кодом завершения.

## Повторение

```sh
make build
python3 -m venv .venv-s3
.venv-s3/bin/python -m pip install -r scripts/requirements-s3-clients.txt
.venv-s3/bin/python scripts/load_pilot.py --binary ./bin/kladovka \
  --mode both --stages 100,1000,5000 --object-bytes 4096 --samples 40 \
  --output /tmp/kladovka-load-result.json
```

`--mode legacy` проверяет один процесс с RF=1; `consensus` — три процесса с RF=3, запросы идут через изначально ведомый узел. Оба режима используют один компьютер и файловую систему; это не распределённый стенд. Для сбора RSS/CPU нужен `ps` с полями rss и time (Linux/macOS). Сам наблюдатель создаёт небольшую дополнительную нагрузку на тот же компьютер. Для быстрого теста самого сценария используйте `--stages 10,25 --samples 3`. В CI выполняется именно такой тест, без порогов скорости: общие runner не дают воспроизводимых численных SLA.

Размер объекта по умолчанию — 4 КиБ, ключи равномерно распределены по 100 группам. Тела объектов одинаковые: это пилот роста каталога. В consensus содержимое может дедуплицироваться по hash чанка; измерения записи, памяти и диска нельзя переносить на уникальные данные. Каталог растёт до каждой указанной ступени; все объекты создаются через S3 PUT, с штатной записью на диск. Поэтому заполнение может занять несколько минут. Допустимы ступени от 1 до 100000, объект до 16 МиБ, общий payload до 2 ГиБ на узел. Перед запуском каждой установки проверяется запас свободного места с учётом копий, метаданных и журнала. Действует серверный порог 256 МиБ свободного места; оценка не резервирует пространство.

## Измерения

- PUT измеряется при заполнении следующей ступени, конкурентность 4, число запросов — прирост каталога.
- GET: 160 запросов при стандартных 40 samples, отдельно конкурентность 1 и 4. Тело каждого ответа сравнивается с исходным.
- LIST: 40 запросов на вариант и конкурентность. Плоская выдача, группировка по `/` и узкий prefix; MaxKeys=100. Имена, группы, размер страницы и IsTruncated проверяются.
- Полный обход: один последовательный проход по всем страницам с проверкой точного множества и порядка ключей. Его время — отдельное наблюдение, не распределение задержек. В этой фазе поле requests означает один составной обход, а фактическое число HTTP-запросов находится в traversal_pages.

Один предварительный GET и по одному запросу каждого вида LIST прогревают клиент и каталог. Эти запросы не входят в выборку. Кеш ОС не сбрасывается. Загрузка замкнутая: следующий запрос рабочего потока начинается после предыдущего. Это измерение при заданной конкурентности, не поиск максимальной пропускной способности и не тест при фиксированной интенсивности поступления запросов.

Латентность измеряется внутри рабочего потока и включает клиентскую подпись, передачу и проверку ответа; время ожидания в очереди executor исключено. Пропускная способность — число успешных операций, делённое на полное время фазы. p50/p95/p99 вычисляются nearest-rank по успешным запросам; ошибки учитываются отдельно и делают прогон неуспешным. При 40 наблюдениях p99 равен максимуму выборки и не является надёжной оценкой редких задержек. Все исходные наблюдения сохранены в JSON.

RSS опрашивается через `ps` примерно раз в 200 мс плюс на границах фаз. Показатель — максимум суммы RSS серверных процессов среди наблюдений; для consensus это три процесса. Он не включает Python-клиент, кеш файлов ОС и не гарантирует обнаружение короткого пика. CPU — прирост суммарного процессорного времени серверов, с точностью платформенного `ps`. Ошибка сбора ресурсов не превращается в нулевое потребление, а делает прогон неуспешным.

Отчёт содержит время UTC, ОС, архитектуру, число логических CPU, версии Python/SDK, параметры, SHA-256 бинарника и сценария, версию бинарника, результаты и состояние consensus после каждой ступени. Запуск на машине с другой нагрузкой, другим диском или настройками может дать иные цифры.

## Область выводов

Включена проверка целостности чтения. TLS, пользовательская политика доступа и аудит в этом пилоте выключены; повторные попытки SDK выключены. Уникальные тела объектов, большие объекты, смешанная запись/чтение, потери сети, длительная нагрузка, восстановление и заполнение диска здесь не измеряются. Функциональные проверки отказов находятся в `consensus_smoke.py`.

Пилот помогает найти зависимость задержки и памяти от размера каталога. Он не устанавливает SLA, RPO/RTO или предельное число объектов. Для эксплуатационного решения нужен отдельный многосерверный стенд с целевой файловой системой, сетью, TLS, аудитом, размерами объектов и профилем запросов.

На ступени 5000, при конкурентности 4:

- Legacy: p95 GET 3,11 мс; LIST flat 661,65 мс; LIST grouped 654,68 мс; LIST narrow 28,64 мс. Полный последовательный обход 50 страниц — 20,48 с. Максимальный наблюдавшийся RSS за ступень — 36,00 МиБ.
- Consensus через follower: p95 GET 437,59 мс; LIST flat 98,04 мс; LIST grouped 93,96 мс; LIST narrow 113,10 мс. Обход 50 страниц — 1,46 с. Максимум суммы RSS трёх серверов — 218,97 МиБ.

Сопоставление стадий указывает на стоимость сканирования legacy-каталога: p95 LIST flat при C=4 вырос с 35,47 мс на 100 объектах до 661,65 мс на 5000. Каждая страница вновь собирает и сортирует весь подходящий каталог; первым кандидатом на оптимизацию становится индекс метаданных с проверяемым восстановлением после сбоя. На момент исходного прогона ускорение ещё не было реализовано; повторный замер приведён ниже.

У наблюдаемого follower после стадий repair_pending составил 71, 937 и 4899; repair_error пуст. Этот счётчик включает незавершённую материализацию локального кеша и повторы восстановления чанков. Он не является числом отсутствующих подтверждённых записей Raft. Авторитетное чтение выполняется из каталога и чанков, а не из кеша; проверенные GET и обходы прошли. Текущий repairLoop выбирает одну запись за тик в секунду, при растущем отсортированном наборе возможны повторные проверки уже обработанных записей. Нужны отдельный замер времени догоняния после остановки записи и доработка очереди с ограничением нагрузки; данный прогон ожидание полного опустошения очереди не выполнял.

Для GET consensus исходный код содержит Barrier и в HTTP-маршрутизации, и в GetObject. Это кандидат для последующего профилирования; текущие измерения не выделяют стоимость каждого барьера. Оптимизация должна сохранить отказ меньшинства и гарантии согласованного чтения.

Следующий порядок: индекс LIST с замером до/после на том же сценарии; очередь материализации с проверкой полного догоняния; затем уникальные/крупные объекты, смешанная нагрузка, TLS и аудит на многосерверном стенде. Численные SLA пока не устанавливаются.

[Исходные измерения с индексом](load-results/2026-10-21-index.json), 02:13–02:25 МСК (20 октября 23:13–23:25 UTC). Сервер c3d3cbe, сценарий cd04aef, SHA-256 сценария и бинарника сохранены в JSON. Тот же компьютер Apple M4/24 ГиБ/APFS, параметры нагрузки, версии Python/SDK и ступени 100/1000/5000. Повторён только legacy; статус passed, ошибок операций, проверки данных и сбора ресурсов нет. Consensus проверен функциональными smoke-тестами, его ускорение этим замером не заявляется.

При C=4 p95 LIST flat на 100/1000/5000 объектах: 14,17 / 18,95 / 16,79 мс вместо 35,47 / 156,94 / 661,65 мс. На 5000 объектах:

- LIST flat: 661,65 → 16,79 мс (примерно в 39 раз меньше).
- LIST grouped: 654,68 → 4,95 мс; LIST narrow: 28,64 → 9,83 мс.
- Полный последовательный обход 50 страниц: 20,478 → 0,152 с. По одному наблюдению на прогон; это не оценка p95 полного обхода.
- Максимальный наблюдавшийся RSS за ступень: 36,00 → 23,63 МиБ. Это наблюдения конкретных запусков; сам индекс хранит O(N) метаданных и не имеет вытеснения.
- GET при C=4: p95 3,11 → 7,29 мс. PUT последних 4000 объектов: p95 283,32 → 317,08 мс. Ускорение чтения тел и записи не подтверждено; причина различий не изолирована двумя последовательными прогонами на рабочем компьютере.

Измерения LIST относятся к **прогретому индексу**: первый запрос исключён методикой. На этом APFS имена имеют алиасы регистра/Unicode; после изменения сбрасываются все индексы и следующий LIST повторно сканирует файлы. Стоимость холодной сборки и смешанных PUT/LIST здесь отдельно не измерена. На файловых системах с точными именами успешные изменения обновляют индекс; вставка/удаление ключа сдвигает отсортированный массив O(N). Холодная сборка держит блокировку хранилища; память пропорциональна сумме объектов проиндексированных полок. Нельзя переносить эти коэффициенты на холодные запросы, смешанную нагрузку или другие файловые системы.

Следующий этап — ограниченная по нагрузке очередь материализации consensus с проверкой справедливого обхода и полного догоняния после остановки записи. Затем нужны измерения холодного/смешанного LIST, уникальные и крупные тела, TLS/аудит и многосерверный стенд.


## Полное догоняние consensus, 21 октября 2026

[Исходный отчёт](load-results/2026-10-21-materialization.json), 07:35–07:37 МСК (04:35–04:37 UTC). Сервер и сценарий из 155444f; SHA-256 бинарника, сценария и общего fixture сохранены в отчёте. Apple M4 / 24 ГиБ / APFS, три отдельных процесса на одном компьютере, без TLS/аудита. Статус passed. Это отдельный сценарий `materialization_pilot.py`, не повтор исходной матрицы задержек GET/LIST.

После предварительной материализации восьми объектов один follower остановлен. При его отсутствии записаны 256 уникальных тел по 4 КиБ с конкурентностью 4, изменён Content-Type прежнего объекта при неизменных байтах и удалены три прежних ключа. После остановки записи запомнена граница applied_index действующего лидера и запущен отсутствовавший процесс.

- Возврат реплики: **22,253 с** до подтверждения полного догоняния всех трёх узлов; максимальное наблюдавшееся repair_pending одного узла — 249. На каждом узле проверены 261 живой объект, его точные байты, SHA-256, ETag, Content-Type и отсутствие трёх удалённых файлов.
- Полный перезапуск трёх процессов с предварительным удалением одного файла временного кеша: **10,074 с** до аналогичного подтверждения; максимальное наблюдавшееся repair_pending — 152.
- В обоих случаях два последовательных наблюдения подтвердили applied_index не ниже границы последней записи, repair_pending=0 и пустой repair_error на каждом узле. После полного рестарта все 261 объекта дополнительно прочитаны через S3 и побайтно сравнены.

Время считается от запуска процессов, включает ожидание статуса с интервалом 200 мс и итоговую физическую проверку файлов; это единичные наблюдения, не p95/RTO. Максимум pending — наблюдавшийся, не гарантированный пик. Меньшее время полного рестарта объяснять только числом записей нельзя: большая часть файлов уже существовала, при первом возврате реплика действительно материализовала пропущенные записи. Исходный пилот на 5000 одинаковых тел не ожидал полного догоняния, поэтому из этих отчётов нельзя вычислить сопоставимый коэффициент ускорения.

Устранён прежний предел одной записи в секунду: теперь FIFO обрабатывается ограниченными пакетами, ошибочные записи не блокируют здоровые, а актуальность поколения проверяется после IO. Ограничения кооперативного бюджета, памяти, периодического обхода и трактовки нулевой очереди описаны в ADMIN.md. Следующий этап — холодные/смешанные LIST, крупные уникальные объекты и нагрузка с TLS/аудитом на отдельных серверах; отдельно нужны длительные испытания нехватки места и повреждения данных.
