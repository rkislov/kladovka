# Нагрузочный пилот

Сценарий `scripts/load_pilot.py` запускает собственные временные серверы на loopback. Внешний endpoint и существующий DATA_ROOT не принимаются. После завершения процессы останавливаются, временные данные удаляются. Результат сохраняется в новый JSON; существующий файл не перезаписывается. При ошибке после начала прогона сохраняется частичный отчёт со статусом failed и ненулевым кодом завершения.

## Повторение

```sh
make build
python3 -m venv .venv-s3
.venv-s3/bin/python -m pip install -r scripts/requirements-s3-clients.txt
.venv-s3/bin/python scripts/load_pilot.py --binary ./bin/kladovka \
  --mode both --stages 100,1000,5000 --object-bytes 4096 --samples 40 \
  --output /tmp/kladovka-load-result.json
```

`--mode legacy` проверяет один процесс с RF=1; `consensus` — три процесса с RF=3, запросы идут через изначально ведомый узел. Оба режима используют один компьютер и файловую систему; это не распределённый стенд. Для сбора RSS/CPU нужен `ps` с полями rss и time (Linux/macOS). Сам наблюдатель создаёт небольшую дополнительную нагрузку на тот же компьютер. Для быстрого теста самого сценария используйте `--stages 10,25 --samples 3`. В CI выполняется именно такой тест, без порогов скорости: общие runner не дают воспроизводимых численных SLA.

Размер объекта по умолчанию — 4 КиБ, ключи равномерно распределены по 100 группам. Тела объектов одинаковые: это пилот роста каталога. В consensus содержимое может дедуплицироваться по hash чанка; измерения записи, памяти и диска нельзя переносить на уникальные данные. Каталог растёт до каждой указанной ступени; все объекты создаются через S3 PUT, с штатной записью на диск. Поэтому заполнение может занять несколько минут. Допустимы ступени от 1 до 100000, объект до 16 МиБ, общий payload до 2 ГиБ на узел. Перед запуском каждой установки проверяется запас свободного места с учётом копий, метаданных и журнала. Действует серверный порог 256 МиБ свободного места; оценка не резервирует пространство.

## Измерения

- PUT измеряется при заполнении следующей ступени, конкурентность 4, число запросов — прирост каталога.
- GET: 160 запросов при стандартных 40 samples, отдельно конкурентность 1 и 4. Тело каждого ответа сравнивается с исходным.
- LIST: 40 запросов на вариант и конкурентность. Плоская выдача, группировка по `/` и узкий prefix; MaxKeys=100. Имена, группы, размер страницы и IsTruncated проверяются.
- Полный обход: один последовательный проход по всем страницам с проверкой точного множества и порядка ключей. Его время — отдельное наблюдение, не распределение задержек. В этой фазе поле requests означает один составной обход, а фактическое число HTTP-запросов находится в traversal_pages.

Один предварительный GET и по одному запросу каждого вида LIST прогревают клиент и каталог. Эти запросы не входят в выборку. Кеш ОС не сбрасывается. Загрузка замкнутая: следующий запрос рабочего потока начинается после предыдущего. Это измерение при заданной конкурентности, не поиск максимальной пропускной способности и не тест при фиксированной интенсивности поступления запросов.

Латентность измеряется внутри рабочего потока и включает клиентскую подпись, передачу и проверку ответа; время ожидания в очереди executor исключено. Пропускная способность — число успешных операций, делённое на полное время фазы. p50/p95/p99 вычисляются nearest-rank по успешным запросам; ошибки учитываются отдельно и делают прогон неуспешным. При 40 наблюдениях p99 равен максимуму выборки и не является надёжной оценкой редких задержек. Все исходные наблюдения сохранены в JSON.

RSS опрашивается через `ps` примерно раз в 200 мс плюс на границах фаз. Показатель — максимум суммы RSS серверных процессов среди наблюдений; для consensus это три процесса. Он не включает Python-клиент, кеш файлов ОС и не гарантирует обнаружение короткого пика. CPU — прирост суммарного процессорного времени серверов, с точностью платформенного `ps`. Ошибка сбора ресурсов не превращается в нулевое потребление, а делает прогон неуспешным.

Отчёт содержит время UTC, ОС, архитектуру, число логических CPU, версии Python/SDK, параметры, SHA-256 бинарника и сценария, версию бинарника, результаты и состояние consensus после каждой ступени. Запуск на машине с другой нагрузкой, другим диском или настройками может дать иные цифры.

## Область выводов

Включена проверка целостности чтения. TLS, пользовательская политика доступа и аудит в этом пилоте выключены; повторные попытки SDK выключены. Уникальные тела объектов, большие объекты, смешанная запись/чтение, потери сети, длительная нагрузка, восстановление и заполнение диска здесь не измеряются. Функциональные проверки отказов находятся в `consensus_smoke.py`.

Пилот помогает найти зависимость задержки и памяти от размера каталога. Он не устанавливает SLA, RPO/RTO или предельное число объектов. Для эксплуатационного решения нужен отдельный многосерверный стенд с целевой файловой системой, сетью, TLS, аудитом, размерами объектов и профилем запросов.

Ограничения кооперативного бюджета, памяти, периодического обхода и трактовки нулевой очереди описаны в ADMIN.md. Следующий этап — холодные/смешанные LIST, крупные уникальные объекты и нагрузка с TLS/аудитом на отдельных серверах; отдельно нужны длительные испытания нехватки места и повреждения данных.

## Холодный и смешанный LIST, крупные уникальные объекты

Отдельный сценарий работает только с временными локальными серверами и не принимает адрес существующей установки:

```sh
python3 scripts/workload_pilot.py --binary ./bin/kladovka \
  --catalog-objects 1000 --cold-samples 3 --samples 40 --mixed-cycles 80 \
  --large-bytes 1048576,8388608 --large-count 8 --output workload.json
```

Зависимости — `scripts/requirements-s3-clients.txt`. По умолчанию последовательно проверяются legacy RF=1 и consensus RF=3 через follower. `--mode legacy|consensus` выбирает один режим. Существующий JSON никогда не перезаписывается; ошибки операций или проверки данных делают прогон failed. Пороги входных параметров и предварительная оценка свободного места ограничивают нагрузку: не более 10000 ключей каталога, 512 МиБ логических крупных тел на узел, до 16 МиБ на объект; оценка запаса учитывает узлы и временные/журнальные копии, но место не резервирует.

Сценарии:

- **Первый LIST после рестарта**: полный перезапуск процессов, ожидание доступности API полок, затем один плоский LIST без прогрева. Время запуска не входит в задержку запроса. Счётчик RSS использует новые PID. Три отдельных наблюдения по умолчанию; это не надёжная оценка p95. Холоден процесс/индекс legacy, а не кеш файлов ОС: кеш ОС не сбрасывается. В consensus каталог восстанавливается Raft; фоновые работы после старта могут влиять на задержку.
- **Прогретый LIST**: плоский и grouped с delimiter `/`, MaxKeys=100, по 40 запросов при конкурентности 1 и 4.
- **Последовательный PUT → LIST flat → LIST grouped**: до 40 перезаписей разных ключей по умолчанию. В исходной сборке на APFS с алиасами регистра/Unicode PUT инвалидировал индекс, поэтому следующий flat LIST измерял пересборку; после оптимизации точные перезаписи сохраняют индекс; grouped идёт после него. На файловых системах с точными именами работает инкрементальное обновление, поэтому этот случай нельзя всегда называть холодным.
- **Смешанные перезаписи и LIST**: четыре работника, 80 циклов; один цикл — PUT, flat LIST, grouped LIST. Размер каталога постоянный, у каждого цикла собственный ключ первой страницы. Проверяются точное множество/порядок ключей, группировка, лимит/IsTruncated, допустимые поколения ETag и видимость собственной уже подтверждённой записи. Отдельные временные интервалы подзапросов показывают фактическое пересечение LIST с PUT; конкурентность сама по себе не доказывает пересечение. По завершении проверяется полный постраничный каталог и байты изменённых объектов.
- **Смешанное создание/удаление**: до 20 циклов с конкурентностью 4, каждый в своём prefix. PUT → LIST с проверкой присутствия → DELETE → LIST с проверкой отсутствия. Это меняющийся набор ключей, но не обещание snapshot-пагинации при конкурентных изменениях. В конце все временные ключи должны отсутствовать.
- **Крупные уникальные тела**: размеры 1 и 8 МиБ, по восемь новых объектов для каждого размера и конкурентности 1/4. SHAKE256 с seed по ключу создаёт разные байты в каждом объекте и каждом 256-КиБ чанке; одинаковые повторяющиеся чанки из прежнего пилота не используются. Генерация тела и вычисление ожидаемых хешей выполняются до измерения PUT. GET читает поток по 1 МиБ, проверяет размер, SHA-256 и ETag. GET идёт после PUT и не является холодным дисковым чтением. На восьми запросах p95/p99 равны максимуму; это наблюдения малой выборки.
- **После нагрузки**: для consensus требуется локальный applied_index каждого узла не ниже границы лидера после записи, repair_pending=0 и пустой repair_error в двух наблюдениях. Затем все крупные локальные копии каждого узла проверяются по размеру и SHA-256. Время ожидания считается после предшествовавших GET, поэтому не равно полному RTO от остановки писателей.

JSON сохраняет исходные задержки, ошибки, интервалы смешанных операций, пропускную способность крупных тел в МиБ/с, наблюдения очереди и хеши уникальных объектов. RSS — выборочный максимум суммы серверных процессов примерно каждые 200 мс, без памяти Python-клиента, его заранее подготовленных тел и кеша ОС. CPU суммируется по серверным процессам; время генерации payload не входит в фазы. Стенд общий с клиентом, нагрузка закрытая, TLS/аудит и SDK-повторы выключены. Нельзя переносить результат на отдельные серверы, другую файловую систему, длительную нагрузку, произвольный профиль записей или SLA. В CI выполняется малый контракт: 25 ключей, один рестарт, тела 1 МиБ, без порогов скорости.

### Что показали профили и что изменилось

В исходном storage CPU-профиле пересборка каталога занимает 1,92 с из 2,03 с CPU-сэмплов (94,6%; это не доля wall time). Теперь точная перезапись/удаление известного ключа сохраняет индекс своей полки; другие индексы сбрасываются из-за возможных алиасов имени полки. Новые ключи, неизвестное написание, ошибки commit по-прежнему требуют безопасной инвалидизации. В финальном профиле пересборка не появляется, всего собрано 0,28 с CPU-сэмплов. Первый LIST после рестарта остаётся полным сканированием под блокировкой.

В consensus суммарное ожидание общей блокировки PUT сократилось с 35,60 до 24,39 с. Внутри одного объекта одновременно подаются до четырёх независимых существующих команд чанков; Raft может объединять поступившие записи. Метаданные публикуются после проверки всех результатов. При ошибке reader/диска/лидерства команды дожидаются завершения до освобождения блокировки. Глобальная блокировка объектов остаётся; квоты, prune, fsync, Barrier и кворум не ослаблены. BatchApplyCh не включён, формат журнала не изменён.

Чтение проверяемого локального чанка теперь выделяет один буфер известного размера с контрольным байтом вместо роста io.ReadAll. Проверки размера и SHA-256 сохраняются. Исходный alloc_space-профиль показывал около 1706 MB в io.ReadAll; финальный — около 359 MB в machine.chunk. Большими источниками аллокаций остаются декодирование msgpack, bytes.growSlice и BoltDB. Alloc_space — накопленные выделения за жизнь процесса, включая подготовку, не RSS и не B/op.

Block-профили суммируют задержки разных горутин: ожидание apply выросло с 22,87 до 47,47 с при уменьшении общего времени, поскольку теперь ожидают несколько работников одновременно. Сравнивать эту сумму с wall time напрямую нельзя.
