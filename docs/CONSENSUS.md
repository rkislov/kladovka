# Восстановление реплик и безопасный failover

Редакция 21 октября 2026 года, актуальная сборка репозитория. Базовый consensus есть в v0.4.0; режим планового обслуживания и последующие оптимизации требуют более новой сборки. Consensus требует пилота на целевом оборудовании; v0.3.0 его не поддерживает. Настройка включается явно и не меняет автоматически существующий кластер.

## 1. Два режима

`CLUSTER_MODE=legacy` — прежний режим по умолчанию: primary по хешу ключа, RF назначает набор копий, успешная запись ждёт назначенные реплики. Он остаётся для совместимости. Автоматического выбора нового primary и догоняющей репликации в нём нет. Инструкция по этому режиму — [ADMIN.md, раздел 6](ADMIN.md#6-кластеризация-и-rf).

`CLUSTER_MODE=consensus` — новый режим: один избранный Raft-лидер обслуживает каталог/данные всего кластера; принимающий узел пересылает ему клиентские запросы. Журнал и снимки содержат данные, порядок операций, версии объектов и отметки удаления. Вернувшийся узел автоматически получает недостающий журнал или снимок, затем восстанавливает локальные файлы. Потерянные/повреждённые блоки восстанавливаются из сохранённого журнала либо по проверенной SHA-256 копии другого участника.

Нужна 64-битная сборка/ОС; 32-битные бинарники сохраняют legacy-режим и отклоняют включение consensus.

Изначально создаётся группа из **3 или 5 голосующих узлов** и **RF, равный числу узлов**. Поддерживается изменение состава в пределах 3–5 участников (раздел 9). Разделение на отдельные группы с RF меньше числа участников и witness не реализованы. Доступна управляемая замена одного участника новым сервером в том же логическом слоте (раздел 8). Двухузловой кластер не переводится в failover простым выбором доступной машины: без третьего голоса безопасного большинства после потери одного узла нет.

Для трёх узлов большинство — два, допускается отказ одного. Для пяти большинство — три, допускается отказ двух. Это требует исправных постоянных дисков и связи между большинством; не относится к одновременной потере всех копий или утрате истории голосования на диске.

## 2. Что считается подтверждённой записью

1. Входящее тело принимается с прежними ограничениями размера/временных файлов.
2. Данные передаются в журнал Raft блоками по 256 KiB, без буферизации всего файла в RAM. У блоков проверяется SHA-256.
3. После блоков отдельная команда публикует метаданные объекта. Незавершённый поток не заменяет предыдущий подтверждённый объект.
4. Успех означает, что данные и публикация подтверждены **большинством** и применены на лидере. Остальные участники догоняют журнал автоматически.

В этом режиме RF — **целевое количество полных реплик**, а не количество обязательных ответов на каждый PUT. При RF=3 запись может быть успешной с двумя доступными узлами. Третий получит данные после возвращения. Файлы `DATA_ROOT/<полка>/<ключ>` являются восстанавливаемыми локальными представлениями; авторитетны журнал/снимки/блоки в `.consensus`, а не наличие файла в одном таком каталоге.

Порядок изменений задаётся индексом Raft, а не часами машин. Удаление сохраняет tombstone; старый файл вернувшегося узла не становится доступным объектом. Каталог и чтение обслуживаются после проверки лидерства/большинства и применения предшествующих операций. Изолированный старый лидер отказывает в изменениях и актуальном чтении, даже если его HTTP-процесс ещё жив.

Сетевой тайм-аут/503 всё равно не доказывает, что запрос не применился: ответ мог потеряться после коммита. Проверяйте результат и повторяйте согласованно. После начала чтения/записи последующий выход или смена лидера не отменяют уже выполненные действия. Режим не является защитой от злонамеренных участников, компрометации общего токена/CA или произвольного удаления файлов администратором.

## 3. Обязательные настройки

- `CLUSTER_MODE=consensus` на всех участниках.
- `RAFT_CLUSTER_ID`: одинаковое уникальное имя новой группы. Сохраните его вместе с конфигурацией; не используйте повторно для другой независимой группы.
- `RAFT_PEERS`: одинаковый JSON-объект `NODE_ID → host:port транспорта Raft`. Участники должны в точности совпасть с NODE_URL/PEER_NODES. Адрес HTTP и адрес Raft имеют разные порты.
- `RAFT_LISTEN_ADDR`: локальный адрес прослушивания Raft. Если не задан, используется адрес своего NODE_ID из RAFT_PEERS.
- `REPLICATION_FACTOR=3` для трёх узлов, `5` для пяти.
- Явный одинаковый `CLUSTER_TOKEN` длиной не менее 16 байт, лучше длинный случайный секрет. Соединение Raft проходит взаимную проверку знания токена и RAFT_CLUSTER_ID через challenge/HMAC; секрет не отправляется открытым текстом.
- `MAX_OBJECT_SIZE`: положительный лимит до 1073741824 байт (1 GiB) включительно. Это текущая граница поддерживаемой конфигурации; временный бюджет и свободное место тоже должны позволять загрузку.
- `CLUSTER_VERIFY_TLS=true`.
- Для внешней сети обязательны HTTPS NODE_URL и `RAFT_TLS_CERT_FILE`, `RAFT_TLS_KEY_FILE`, `RAFT_TLS_CA_FILE`. Проверка TLS не отключается. Сертификат транспорта должен содержать DNS/IP адреса из RAFT_PEERS; CA-файл нужен для проверки сертификатов других участников. Сертификаты должны быть действующими.
- Незашифрованный транспорт разрешён только когда все объявленные адреса и фактический Raft/HTTP listener находятся на loopback. `0.0.0.0` не является loopback. Это режим локального тестирования, не удалённого рабочего кластера.

HTTP-пиры проверяют HTTPS через системное хранилище CA; RAFT_TLS_CA_FILE относится к транспорту Raft. Для внутреннего CA настройте доверие и там, и там. Общий токен не заменяет шифрование канала и сетевые ограничения.

## 4. Пример трёх серверов

Подготовьте отдельные серверы/диски, установите службу по [инструкции администратора](ADMIN.md#4-установка-на-linux-с-systemd). На **новых пустых DATA_ROOT** задайте общую часть env-файла:

```ini
CLUSTER_MODE=consensus
RAFT_CLUSTER_ID=storage-group-20261020
RAFT_BOOTSTRAP=true
RAFT_PEERS='{"s1.storage.example.org:8443":"s1.storage.example.org:9000","s2.storage.example.org:8443":"s2.storage.example.org:9000","s3.storage.example.org:8443":"s3.storage.example.org:9000"}'
RAFT_LISTEN_ADDR=0.0.0.0:9000
REPLICATION_FACTOR=3
REGION=us-east-1
DATA_ROOT=/var/lib/kladovka
LISTEN_ADDR=:8443
CLUSTER_TOKEN=REPLACE_WITH_THE_SAME_LONG_RANDOM_CLUSTER_SECRET
ACCESS_KEY=cluster-client
SECRET_KEY=REPLACE_WITH_THE_SAME_LONG_RANDOM_S3_SECRET
ADMIN_USER=operator
ADMIN_PASSWORD=REPLACE_WITH_THE_SAME_LONG_RANDOM_ADMIN_PASSWORD
CLUSTER_VERIFY_TLS=true
MAX_OBJECT_SIZE=1073741824
MAX_TEMP_BYTES=2147483648
MIN_FREE_DISK_BYTES=268435456
TLS_CERT_FILE=/etc/kladovka/tls/fullchain.pem
TLS_KEY_FILE=/etc/kladovka/tls/key.pem
RAFT_TLS_CERT_FILE=/etc/kladovka/tls/fullchain.pem
RAFT_TLS_KEY_FILE=/etc/kladovka/tls/key.pem
RAFT_TLS_CA_FILE=/etc/kladovka/tls/ca.pem
```

Замените секреты на реальные одинаковые значения на всех участниках. Файловые пути одинаковы по имени, но каждый сервер имеет свой каталог данных и подходящий ему сертификат. Можно использовать один сертификат для своего HTTP и своего Raft listener, если его назначение и SAN подходят; общего приватного ключа всем серверам не требуется.

Индивидуальная часть A:

```ini
NODE_ID=s1.storage.example.org:8443
NODE_URL=https://s1.storage.example.org:8443
PEER_NODES=https://s2.storage.example.org:8443,https://s3.storage.example.org:8443
```

B:

```ini
NODE_ID=s2.storage.example.org:8443
NODE_URL=https://s2.storage.example.org:8443
PEER_NODES=https://s1.storage.example.org:8443,https://s3.storage.example.org:8443
```

C:

```ini
NODE_ID=s3.storage.example.org:8443
NODE_URL=https://s3.storage.example.org:8443
PEER_NODES=https://s1.storage.example.org:8443,https://s2.storage.example.org:8443
```

Откройте HTTP(S) и Raft порты между участниками, ограничив их доверенной сетью; клиентам нужен HTTP(S), не Raft. Один DATA_ROOT — один процесс. При ACCESS_POLICY_FILE настройте одинаковые политики и ключи на всех серверах; общий S3 bootstrap-ключ тогда отключается, как в обычном режиме.

Запустите три службы. `RAFT_BOOTSTRAP=true` нужен **только для первого создания новой пустой группы** с совершенно одинаковой конфигурацией у всех голосующих участников. После проверки лидера/записи уберите флаг или установите false во всех env-файлах; поочерёдно перезапустите по одному узлу с проверкой возврата и восстановления большинства перед следующим.

Нормальный повторный запуск использует сохранённую конфигурацию, term/vote, журнал и снимки. При потере raft.db существующий узел не должен создавать новую независимую историю. Не удаляйте `.consensus`, identity/bootstrapped marker, корневой .kladovka-consensus и не включайте bootstrap для «починки» работающей группы. Полная потеря постоянного Raft-состояния требует отдельной согласованной процедуры восстановления, а не обычного автоматического возврата процесса.

## 5. Проверка и наблюдение

Проверьте `/cluster` каждого узла с административной авторизацией. В поле `consensus` доступны:

- `state`: Leader/Follower/Candidate и другие локальные состояния Raft;
- `leader`: известный HTTP URL лидера;
- `term`: срок Raft;
- `applied_index`: индекс последней применённой команды данных;
- `voters`, `quorum`: размер группы и необходимое большинство;
- `repair_pending`, `repair_error`: последняя локальная оценка очереди/ошибок восстановления;
- `tombstones`: локальное количество сохранённых отметок удаления.

```bash
curl --fail --user "$ADMIN_USER:$ADMIN_PASSWORD" "$NODE_ENDPOINT/cluster"
```

Prometheus `/metrics` отдаёт локальные gauges `kladovka_consensus_enabled`, `kladovka_consensus_leader`, `kladovka_consensus_applied_index`, `kladovka_consensus_repair_pending`, `kladovka_consensus_quorum_required`. Последняя — требуемый размер большинства, не число доступных голосов. Сравнивайте индексы/очереди по отдельным узлам; локальный leader-флаг не заменяет успешный кворумный запрос.

`/healthz` остаётся проверкой живого HTTP-процесса, а не готовности к консенсусной записи. Для готовности проверяйте успешный авторизованный запрос к каталогу и контрольный PUT/GET. Узел без большинства может отвечать health=200 и возвращать 503 на данные — это ожидаемое безопасное поведение.

`/api/stats` и LIST в этом режиме используют каталог лидера всего кластера. Счётчики операций и заполнение физического диска относятся к процессу, обслужившему запрос. Панель различает глобальный каталог, целевой RF и размер кворума. Локальный repair_pending не является суммой отставания всех серверов; сравнивайте состояние каждого узла и проверяйте данные. Он обновляется в фоне, поэтому не служит подтверждением завершения конкретного клиентского PUT.

При приёмке создайте новую тестовую полку, загрузите новый ключ через любой endpoint, скачайте через другой и сравните SHA-256. На отдельном стенде остановите лидера, дождитесь нового лидера и повторите запись; затем верните старый узел и проверьте схождение. Удалите тестовый ключ при отключённом узле и убедитесь, что после его возвращения ключ не появился снова. При отключении двух из трёх серверов проверяйте **отказ**, а не успех записи.

Автоматическая проверка со своими временными каталогами и тремя процессами:

```bash
make build
python3 scripts/consensus_smoke.py --binary ./bin/kladovka
```

Для сценария нужен AWS CLI. Сценарий проверяет потоковую запись, пересылку SigV4 и presigned GET через follower, multipart/ETag/Range, возврат узла после пропущенных изменений, смену лидера, сохранность подтверждённых данных и отказ при потере большинства. Go-тесты дополнительно проверяют сетевую изоляцию работающего старого лидера, восстановление повреждённого блока после compaction, полный рестарт из снимков, прерванный PUT и очистку блоков при открытом снимке/чтении. Это функциональные проверки, не аппаратные испытания отключения питания и не численный SLA.

## 6. Multipart, место и фоновая работа

Завершённый multipart-объект проходит тот же консенсусный commit. Незавершённые части по-прежнему локальны текущему лидеру. После смены лидера UploadId может быть недоступен; проверьте, не завершён ли объект, затем при необходимости начните загрузку заново. Автоматический перенос незавершённых multipart-сеансов здесь не обещается.

Журнал, блоки и снимки занимают **дополнительное место сверх видимых объектов**. Квота объектов/частей не является квотой Raft-журнала и снимков. Не применяйте оценку `N × C / RF` как готовую доступную ёмкость этого режима. Для файла могут одновременно существовать временное тело, блоки, журнал, локальное представление и снимки; после compaction старые данные также могут сохраняться в двух последних снимках.

Фоновый проход ограничивает число проверяемых блоков и локальных объектов за итерацию; при ошибках получения блоков используется backoff до минуты. Неиспользуемые блоки очищаются согласованной командой лидера после завершения текущих записей, при наступлении минутного срока фоном либо перед следующей операцией записи под writeMu. Уже начатая запись и отсутствие кворума могут задержать очистку. Открытые снимки и чтения удерживают свои блоки до завершения. Tombstones не удаляются автоматически: это защита от возврата старых объектов. Данные каталога/удалений и нагрузка на диск требуют наблюдения и пилотного sizing.

Текущий предел JSON-каталога снимка — 64 MiB (метаданные, ссылки блоков и tombstones, без содержимого объектов). При превышении снимок отклоняется, журнал продолжает расти; контролируйте размер каталога и диска до достижения этой границы.

При исчерпании диска исправьте причину на узле и наблюдайте догоняющее восстановление. Не освобождайте место удалением raft.db, снимков, файлов блоков или tombstones вручную. Если большинство потеряло свои постоянные данные, автоматическое восстановление без внешней копии невозможно.

## 7. Переход и эксплуатационные ограничения

Существующие legacy-полки не импортируются в новый журнал автоматически. Нужен новый пустой консенсусный кластер и контролируемая миграция GET → проверка SHA-256 → PUT с объединённым каталогом источника. До переключения клиентов сохраните остановленные резервные копии старого кластера. Не запускайте разные протоколы поверх одних файлов; текущий бинарник отказывается открывать consensus DATA_ROOT в legacy-режиме.

Первоначальные RAFT_PEERS и RF, идентификатор группы и NODE_ID фиксируются в дисковой идентичности. Текущий состав сохраняется отдельно в Raft. Изменение JSON/переменных не выполняет безопасную reconfiguration и отклоняется при несоответствии идентичности. Добавление/вывод в пределах 3–5 участников выполняется только через API из раздела 9. Возврат узла с сохранённым журналом поддерживается автоматически; для замены пустым сервером выполняйте раздел 8. Нельзя просто забыть старый голос и запустить bootstrap поверх потерянного состояния.

Резервируйте **весь DATA_ROOT, включая .consensus и .kladovka-consensus**, конфигурацию, политики, сертификаты и бинарник. Видимые полки без .consensus не являются резервной копией этого режима. Согласованная остановленная копия всех участников остаётся понятным вариантом восстановления; проверяйте её на изолированном стенде. Не объединяйте разновременные каталоги Raft вручную и не используйте force-bootstrap для восстановления записи в меньшинстве.

Политики доступа, сеансы панели и внешняя конфигурация не реплицируются Raft-журналом объектов. На другом адресе панели нужен отдельный сеанс; действующий сеанс доступного входного узла может продолжать пересылать действия новому лидеру с серверной авторизацией. Это не кластерный SSO. Обновление политик и CA всё ещё требует согласованной доставки администратором.

Используется [HashiCorp Raft](https://github.com/hashicorp/raft/tree/v1.8.0) и постоянный BoltDB backend; версии/checksums закреплены в go.mod/go.sum. Сборка теперь скачивает закреплённые Go-зависимости; работа бинарника по-прежнему не требует внешнего сервиса консенсуса. Лицензии и ссылки на исходники — в [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).


## 8. Замена потерянного узла новым сервером

Процедура заменяет один **существующий логический слот** без переноса всего кластера. Она не увеличивает целевой RF и не разрешает работу без большинства. До начала обновите **все** участники до сборки с поддержкой замены, с согласованным окном обслуживания и резервной копией; смешанный кластер со старой реализацией FSM не поддерживается.

### Подготовка

1. Убедитесь, что оставшиеся участники имеют большинство и проходят кворумный GET/PUT. Если потеряно большинство, эта процедура не поможет: требуется проверенная резервная копия.
2. Остановите и изолируйте заменяемый процесс/сервер. Сохраните его диск для диагностики. Не запускайте второй процесс поверх тех же файлов. Текущий лидер не заменяется: сначала верните другое большинство и перенесите обслуживание/дождитесь нового лидера после штатной остановки прежнего.
3. Новый сервер принимает прежний HTTP NODE_URL/NODE_ID (перенос DNS/IP выполняется администратором). `RAFT_PEERS`, RAFT_CLUSTER_ID, RF, политики и межузловой токен остаются теми же. Подготовьте **новый пустой DATA_ROOT**. Сертификаты должны подходить адресам нового сервера.
4. Выберите **новый порт Raft, никогда ранее не использованный в этой группе**. Это обязательное ограничение первой реализации: исключается повторное использование портов исходных, текущих и выведенных участников, включая адресные алиасы. Не перенаправляйте старый Raft-порт на новый. Старый изолированный лидер не должен получить подтверждение от пустого сервера по адресу прежней реплики.

Для замены s3 из примера добавьте на новом сервере:

```ini
NODE_ID=s3.storage.example.org:8443
NODE_URL=https://s3.storage.example.org:8443
DATA_ROOT=/var/lib/kladovka-replacement
RAFT_BOOTSTRAP=false
RAFT_JOIN=true
RAFT_REPLACEMENT_ADDR=s3.storage.example.org:9001
RAFT_LISTEN_ADDR=0.0.0.0:9001
```

Остальные настройки скопируйте из конфигурации этого слота, сохраняя исходный RAFT_PEERS с портом 9000. `RAFT_REPLACEMENT_ADDR` закрепляется в идентичности на диске, оставьте его и новый listener при всех следующих запусках. Порт listener должен совпадать с объявленным новым портом. Откройте его остальным участникам; HTTP(S) и требования TLS сохраняются.

### Приём кандидата

Запустите новый процесс. Он создаст уникальный `raft_id` вида `NODE_ID#<случайный идентификатор>`, но **не выполняет bootstrap и не голосует**. Сохраните DATA_ROOT кандидата: перезапуск обязан использовать ту же историю и тот же raft_id.

С адреса нового сервера получите локальный идентификатор:

```bash
curl --fail --user operator https://s3.storage.example.org:8443/cluster
```

Скопируйте `consensus.raft_id`. На любом доступном участнике, кроме ещё не принятого кандидата, отправьте административный запрос. Curl запросит пароль; JSON не содержит секретов:

```bash
curl --fail --user operator \
  -H 'Content-Type: application/json' \
  -d '{"node_id":"s3.storage.example.org:8443","raft_id":"s3.storage.example.org:8443#ЗАМЕНИТЕ_НА_ИДЕНТИФИКАТОР_ИЗ_CLUSTER"}' \
  https://s1.storage.example.org:8443/api/cluster/replace
```

Ответ **202 означает запись намерения**, а не окончание синхронизации. Повтор с тем же raft_id идемпотентен. Запрос требует роли admin; browser-сеанс дополнительно требует обычный CSRF-токен. У ограниченных reader/writer доступа нет. Действие попадает в обычный аудит; намерение и завершение сохраняются в журнале Raft.

Лидер последовательно подтверждает удаление прежнего голосующего участника, добавляет новый raft_id как **Nonvoter**, передаёт журнал/снимок, проверяет применённый индекс и SHA-256 всех блоков кандидата, затем делает его **Voter**. Одновременно выполняется только одна замена. После рестарта кандидата или смены лидера процесс продолжается из сохранённого намерения. Во время проверки готовности изменения каталога могут ненадолго ожидать; проверка кандидата ограничена 30 секундами и при тайм-ауте повторяется. Для больших каталогов нужен отдельный нагрузочный пилот.

### Контроль и завершение

Проверяйте `/cluster` на действующем лидере:

- `consensus.members`: реальные Raft-участники, адреса и `suffrage`;
- `consensus.replacement`: старый/новый raft_id, адрес и `done`;
- `consensus.replacement_error`: причина ожидания/ошибка последней попытки;
- `consensus.voters` и `quorum`: фактический состав на текущем этапе, а не целевой RF.

В панели отображаются этап замены и последняя ошибка. Замена завершена при `replacement.done=true`, новом участнике Voter и восстановлении исходных 3/5 голосов. Проверьте контрольный GET/PUT, SHA-256 и отсутствие ранее удалённого тестового объекта. Затем уберите `RAFT_JOIN` или установите false: новый raft_id уже сохранён. Сохраняйте RAFT_REPLACEMENT_ADDR и обновите резервные копии/описание сетевых портов.

Во время замены трёхузлового кластера после исключения старого участника остаются два голосующих: для записи нужны оба. Дополнительный отказ приостановит операцию и запись. Это ожидаемая потеря доступности, а не повод делать force-bootstrap.

Если кандидат ещё догоняет данные, устраните сеть/диск/сертификаты и перезапустите **тот же** DATA_ROOT. Не удаляйте журнал кандидата и не запускайте второй RAFT_JOIN, пока операция ожидает его raft_id. Переназначение уже начатой замены на другой пустой кандидат в этом этапе не реализовано; при утрате его диска требуется восстановить его резервную копию либо отдельная процедура восстановления. Автоматического отменяющего API нет.

Тесты проверяют пустой сервер, стадию Nonvoter, восстановление после перезапуска кандидата и лидера, сохранение данных/tombstones, участие нового узла в кворуме и отказ прежней инкарнации в записи. Трёхпроцессный smoke дополнительно перезапускает весь кластер после замены.

## 9. Добавление и вывод участников

Поддерживаются последовательные переходы **3 ↔ 4 ↔ 5 голосующих узлов**, RF=N. Четыре узла требуют трёх голосов и, как три узла, выдерживают потерю только одного. Пять требуют трёх голосов и выдерживают потерю двух. RF меньше N, witness и группы больше пяти пока не поддерживаются.

Перед изменением обновите все оставшиеся участники до сборки с membership protocol 2. Лидер проверяет эту возможность через защищённый внутренний API. Нужен работающий кворум, резервная копия и свободный диск для полной копии данных. Одновременно допускается одна операция добавления, вывода или замены.

**Не переписывайте RAFT_PEERS и REPLICATION_FACTOR после изменения состава.** Они описывают первоначальную группу и участвуют в проверке идентичности DATA_ROOT. Текущая топология, HTTP-адреса и целевой RF сохраняются в Raft и восстанавливаются после полного перезапуска. Существующие узлы сохраняют исходные PEER_NODES; новый узел перечисляет в PEER_NODES все исходные HTTP-адреса, кроме своего, если он входил в исходную группу. Адреса уже выведенных стартовых участников могут оставаться в этих настройках.

### Добавление

1. Подготовьте новый HTTP NODE_URL/NODE_ID, отдельный пустой DATA_ROOT, политики, токен и TLS, как у действующей группы. Сохраните исходные RAFT_PEERS, REPLICATION_FACTOR и RAFT_CLUSTER_ID.
2. Установите `RAFT_BOOTSTRAP=false`, `RAFT_JOIN=true`, `RAFT_REPLACEMENT_ADDR` с новым, никогда не использованным в группе портом и соответствующий `RAFT_LISTEN_ADDR`. Эти параметры применяются и к добавляемому узлу. Не направляйте старые Raft-порты на новый процесс.
3. Запустите процесс и получите `consensus.raft_id` через его `/cluster`. До допуска обращения к данным возвращают 503.
4. На действующем участнике отправьте запрос роли admin:

```bash
curl --fail --user operator -H 'Content-Type: application/json' \
  -d '{"request_id":"expand-fourth-20261020","http_url":"https://s4.storage.example.org:8443","raft_id":"s4.storage.example.org:8443#ИДЕНТИФИКАТОР_ИЗ_CLUSTER"}' \
  https://s1.storage.example.org:8443/api/cluster/add
```

Новый участник сначала становится Nonvoter. Лидер проверяет применённый индекс и SHA-256 всех блоков перед переводом в Voter. Данные распределяются как полные копии; удаления старых копий ради ребаланса здесь нет. HTTP-маршрутизация и обнаружение реплик используют сохранённую топологию.

### Вывод

```bash
curl --fail --user operator -H 'Content-Type: application/json' \
  -d '{"request_id":"remove-fourth-20261020","node_id":"s4.storage.example.org:8443"}' \
  https://s1.storage.example.org:8443/api/cluster/remove
```

Вывод ниже трёх участников отклоняется. Перед удалением голоса проверяется актуальность данных кворума будущего состава. Сам выводимый узел может быть недоступен. Если выводится лидер, он передаёт лидерство проверенному участнику; новый лидер продолжает сохранённую операцию. Дополнительный отказ может остановить её до восстановления кворума.

### Контроль, повтор и остановка

Ответ 202 подтверждает намерение. На текущем лидере `/cluster` показывает `consensus.membership_change` (`request_id`, `kind`, `node`, `target_rf`, `done`), `membership_error`, действительные `members`, `voters` и `quorum`. Панель показывает фазу и ошибку. `replication_factor` в статистике — целевое число копий; фактическое число голосов смотрите отдельно.

Дождитесь `done=true`, проверьте данные и число Voter. Только затем остановите выведенный процесс и уберите его из внешнего балансировщика. Файлы не удаляются автоматически; сохраните их по политике резервирования. HTTP-слот выведенного узла нельзя повторно добавить этим API, используйте новый адрес. Для замены действующего слота предусмотрен раздел 8.

`request_id` — уникальная строка из 1–128 латинских букв, цифр, `_` или `-`. Повтор того же запроса с тем же идентификатором безопасен, включая потерю ответа и завершённую операцию. Использование идентификатора для другого действия отклоняется. После перезапуска лидера или кандидата операция продолжается. Сохраняйте DATA_ROOT кандидата: отмена и переназначение незавершённой операции при потере его диска пока не реализованы. Не применяйте force-bootstrap и не удаляйте журнал ради продолжения.

Проверки включают переход 3→4→5→4→3, вывод лидера, идемпотентность, сохранение состава после рестарта и реальный HTTP API на пяти отдельных процессах.


## 10. Плановое обслуживание узла (после v0.4.0)

Этот API добавлен в следующую разработку после релиза v0.4.0; опубликованные бинарники v0.4.0 его ещё не содержат. Обновите **всех** участников до сборки с membership protocol 3. Режим доступен только для consensus. В отличие от вывода участника, он сохраняет голос, состав и RF. Одновременно допускается один обслуживаемый узел; добавление, вывод и замена на это время запрещены.

Перед началом завершите или отмените multipart-загрузки, подготовьте резервную копию и уберите выбранный endpoint из внешнего балансировщика. Между запросами multipart не считается активным HTTP-потоком; его временные части не становятся переносимыми от смены лидера. Используйте отдельный уникальный request_id на каждый цикл обслуживания.

```bash
curl --fail --user operator -H 'Content-Type: application/json' \
  -d '{"request_id":"service-20261020","node_id":"s2.storage.example.org:8443","action":"enter"}' \
  https://s1.storage.example.org:8443/api/cluster/maintenance
```

Ответ **202** подтверждает запись намерения в Raft, а не разрешение остановки. На выбранном узле новые запросы к данным получают **503** и Retry-After: 5. Уже принятые HTTP-потоки завершаются; зависший поток задерживает обслуживание без принудительного обрыва. Если выбран лидер, он передаёт роль проверенному участнику. Репликация, внутренний API, /healthz, /metrics, /cluster, UI и авторизованная статистика продолжают работать. /healthz — проверка процесса, а не готовности принимать данные.

Следите за consensus.maintenance на текущем лидере через /cluster или панель: request_id, node_id, raft_id, ready, done. Поле maintenance_error объясняет задержку, active_requests показывает число активных запросов на опрашиваемом узле. Перед первым запросом после рестарта узел дожидается применения подтверждённого лидером поколения каталога: сохранённое обслуживание не обходится через перезапуск.

Дождитесь **ready=true**, затем непосредственно перед остановкой выполните:

```bash
curl --fail --user operator -H 'Content-Type: application/json' \
  -d '{"request_id":"service-20261020","node_id":"s2.storage.example.org:8443","action":"check"}' \
  https://s1.storage.example.org:8443/api/cluster/maintenance
```

Только **200** подтверждает текущую проверку: обслуживаемый узел не лидер, а остальные сохраняют большинство **исходного неизменённого состава** и проверенные SHA-256 подтверждённых данных. ready хранит факт завершения drain и не заменяет эту повторную проверку. При 409 не останавливайте узел: устраните причину и повторите check. Новый отказ после проверки всё равно может лишить кластер кворума. Остановку службы выполняет администратор, API её не выполняет.

После работ запустите ту же службу с прежним DATA_ROOT, настройками и Raft-идентичностью. Режим обслуживания сохраняется после рестарта. Для возврата:

```bash
curl --fail --user operator -H 'Content-Type: application/json' \
  -d '{"request_id":"service-20261020","node_id":"s2.storage.example.org:8443","action":"exit"}' \
  https://s1.storage.example.org:8443/api/cluster/maintenance
```

Выход разрешён только после проверки актуального индекса и всех блоков вернувшегося участника. При 409 дождитесь синхронизации и повторите exit. При 200 дождитесь done=true и успешного чтения контрольного объекта, затем верните endpoint в балансировщик. Повтор enter/exit с прежним идентификатором безопасен; завершённый идентификатор не запускает новый цикл. Потерю диска во время обслуживания нельзя исправить удалением журнала или force-bootstrap: требуется восстановление прежнего состояния, автоматического переназначения незавершённого обслуживания пока нет.

Метрики kladovka_consensus_maintenance_active, kladovka_consensus_maintenance_local, kladovka_consensus_maintenance_drained и kladovka_consensus_active_requests опубликованы в /metrics. Обслуживание не отключает алерты автоматически.
